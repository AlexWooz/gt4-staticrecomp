Read-only audit of **scene-specific special-casing, the license B-1 stutter and the measurement method**, written for the
owner's 2026-11-10 17:59 direction: CoreGS 2.0 is still far from the expected performance; a streamer with a Ryzen 5 5600

suspects the George V Paris work was overfit and that 10x/12x is the wrong measurement target — 3x/Full HD and 6x/4K are
the realistic baselines.

- No builds, benchmarks or game runs; no code/data/pin/test changes. Every number is quoted from the owner/TASK-215

## 0. The short answer

**There is no `if (track == George V)` in `native/hw_gs`.** A case-insensitive search of the renderer finds no track name
used as a key, condition or address, and no guest address in the runtime path; the mentions of George V/night in comments
and fixtures are prose/test data, not branches. The draw paths are keyed by GS state, formats, sizes and target
relationships. The George V/night optimisations the owner remembers are **game-mechanism** optimisations, not track ones:
the flare table (the game's light visibility read), the CLUT loads (the game's palettes), the readback-before-write, the
GLM pages, the tone/colour filter, the depth clear and the depth fill. They generalise to any scene that uses the same GS
mechanism; the license uses the **CLUT** (1,430 flushes/VBlank) but has **no flare**, so the flare work cannot help it,
and the CLUT work does.

**The overfit is real, but it lives in three other places:**

1. **The empirical shader-variant list** (`core2_known_variants.inc`: 544 keys generated by `known_variants.py` from the
   sessions that existed; IN-507's own note says it is "what those scenes and sessions asked for, not every state the
   game could reach"). A track/mode/card outside that sample compiles new variants during play and draws with the uber
   pipeline until they are ready; a weaker CPU pays more. This is the strongest candidate for a track that stutters on one
   machine and not another.
2. **The performance-mode thresholds/effect keys** (road sheen, alpha fills, effect targets ≤256, CPU sprites ≤64×64, the
   flare table's 64×8/128-qword pattern). They are game-effect or size heuristics, not track keys, but they were chosen on
   the night/George V/HD 620 scenes; a different track can miss the intended effect or hit a false positive.
3. **The measurement emphasis** (George V/night/10x-12x, `cpu_summary.py` p50/p95 averages) rather than the code. The
   license is CPU-bound: the 9060 XT's GS worker is **8.92 ms**, GPU **1.04 ms**, wall **10.01 ms**, frame p50 **10.58
   ms**, with **1,430 CLUT flushes/VBlank (1,010 same texture)** and **gif_parse 3.93 ms**; the RTX 3060 laptop's GS
   worker is **19-20 ms** with GPU 7-10 ms (TASK-171). The laptop's GS worker is already over 16.7 ms before the frame
   starts missing; the 9060 XT's 8.92 is below it. The GPU has headroom on both (1.04 ms / 7-10 ms). That is a
   **CPU/front-end/CLUT** stutter, not a rasterisation one, and the p50 hides its tail.

**The first fixes are therefore the license/weak-GPU path, not 12x:** the per-primitive front end (TASK-171), several
palettes in one batch (TASK-168), the cheap CLUT-flush scope and the SCISSOR/XYOFFSET batching (TASK-215b), the known-
variant coverage, the weak-GPU submission/present path, and a measurement matrix at **3x/Full HD and 6x/4K** with p99,
1% low and >16.7/>20 ms counts. 10x/12x stays diagnostic only. The GPU flare (TASK-215c) is still the night/6x item; it
is not the license item.

## 1. Scene-specific special-casing audit

**Method.** Case-insensitive search of `native/hw_gs` for track/scene words (`night`, `license`, `photo`, `showroom`,
`race`, `George`, `Hong Kong`, `Tokyo`, `Nürburgring`, `rally`, `rain`), guest addresses (`0x` in runtime code), resolutions
(`640`, `448`, `256`, `512`), frame/VBlank thresholds, `GT4_CORE2_*`/`GT4_HW_*` defaults and the known-variant list. Each
hit was read in context. The result:

### 1.1 No track/scene/address hardcode in the runtime path

- No track names, no scene ids, no `if (night)`, no `if (license)`, no guest render addresses **used as keys or
  conditions** in `core2_renderer.cpp`, `core2_gpu.cpp`, `hw_gs_stream_sink.cpp`, `hw_gs_backend.cpp` or the shaders;
  track names appear only in comments, and the only guest addresses in `native/hw_gs` are in **test fixtures**
  (`core2_depth_alias_fixture.cpp` uses BP 11200/11232 to test the depth-fill rule); a fixture is not a scene special
  case.
- The renderer is keyed by **GS state** (`PRIM`, `TEST`, `FRAME`, `ZBUF`, `TEX0/1`, `ALPHA`, `CLAMP`, `SCANMSK`, `FBA`,
  `FBMSK`), target base/width/format/class, rectangle relationships and image sizes. That is generic across tracks.
- `lastSceneFrame_` (`core2_renderer.cpp:3884-3922`) sounds scene-keyed but is a **stateful depth-clear helper**: it
  remembers the last frame register a batch wrote with a non-`0xFFFFFFFF` FBMSK so `RewriteDepthClear` can retarget GT4's
  depth clear (`IN-529`). It is keyed to a GS pattern, not a track; a scene whose clear does not follow the pattern keeps
  the written path. It is generic with a risk if a scene writes a frame register before its first masked frame.
- The **frame skip/30 fps** and camera/FOV hooks live in `native/frame_skip.cpp`, `native/game_target.hpp`,
  `native/camera_360*`, `native/fov*`, not in `native/hw_gs`; they are game-level features, not renderer scene keys.

**What is not a special case:** the George V/night flare readback, CLUT, GLM pages, drawn-page test, readback-before-
write, width grace, pacer/present and swapchain work are **game-mechanism or device** paths. They are not keyed to a
track; they generalise to any scene with the same mechanism. The owner's "the optimisation was applied only to that
track" is true of the **effort and acceptance scenes**, not of the code's keys: the code is generic, the sample is narrow.

### 1.3 The one thing that is genuinely "trained" on scenes

`core2_known_variants.inc` (544 keys) is the only artifact built by **running scenes** and committed. It is not a hardcoded
track: it is the union of `variants.bin` from the sessions in `known_variants.py`, and `IN-507` states the limit. The
risk is concrete: a scene/card not in the sample compiles new specialised pipelines during play (`IN-437`: about 128 ms
per variant on the worker, max 250 ms; the uber pipeline meanwhile) and, on a weaker CPU, can stutter. The license B-1,
the GTX 1660, the streamer's 5600/1660 and the rain/rally scenes are the obvious candidates for new states. The
`[core2] specialised pipelines ... uber_batches` line (`core2_renderer.cpp:5016-5023`) and `shaders.log` answer it; no
stored log in the tree has the license.

## 2. Why the license B-1 oval can stutter on the weaker RTX 3060 but not on the 9060 XT

### 2.1 The measured facts

| Fact | Value | Source | Label |
|---|---|---|---|
| 9060 XT (Ryzen 7 5700X), license 1x, GS worker | 8.92 ms/VBlank | Owner/TASK-215 measurement, 2026-11-10 | C |
| 9060 XT, wall / frame p50 / GPU busy | 10.01 / 10.58 / 1.04 ms | same | C |
| 9060 XT, CLUT flushes / same texture | **1,430 / 1,010 per VBlank** | same | C |
| 9060 XT, `gif_parse` | **3.93 ms/VBlank** | same | C |
| RTX 3060 laptop (i7-11800H), license 1x, GS thread | **19-20 ms** | TASK-171 (headless, rc13/rc14 plain) | C |
| RTX 3060 laptop, VU1 / EE / GPU busy | about 15 / 13 / 7-10 ms | TASK-171 | C |
| RTX 3060 laptop, primitives / batches | 26,000-27,000 / 1,930 per VBlank | TASK-171 | C |
| George V 1x, for scale | GS 8.0 ms; CLUT 2.0 ms; 1,494-1,631 CLUT flushes | TASK-134 section 9 | C |

The 9060 XT's **GPU is 1.04 ms** and its GS worker 8.92: the frame is CPU. The RTX 3060 laptop's **GS worker 19-20 ms**
exceeds the 16.7 ms budget while its GPU is 7-10 ms: the frame is CPU. The difference is the **GS-worker CPU path**
(front end/CLUT/batches/driver), not rasterisation, not the flare (the license has none), not the GPU.
### 2.2 The hypothesis

- **C:** the license is CPU/GS-worker-bound on both machines. The 9060 XT's 8.92 < 16.7 (no stutter); the RTX 3060
  laptop's 19-20 > 16.7 (stutter). The GPU is idle on both (1.04 / 7-10 ms).
- **H:** the GS-worker cost is dominated by the **per-primitive front end** (`gif_parse` 3.93 ms on the 9060 XT; 26-27k
  primitives/1,930 batches) and the **CLUT-load batch flushes** (1,430, 1,010 same texture; each flush is a batch through
  the renderer/driver; TASK-134 measured the CLUT path at 2.0 ms on George V for ~1,500 flushes). On the laptop's
  i7-11800H, the same per-primitive and per-flush work costs more (single-thread, power/thermal), pushing the GS worker to
  19-20 ms. The NVIDIA driver's per-draw calls may add to the `draw` stage relative to the 9060 XT's AMD driver (Hyp; the
  `[core2] exclusive`/sampler on the laptop would show).
- **Hyp:** the stutter is the **tail**, not the p50: the 9060 XT's p50 is 10.58 (below 16.7), but a scene with 1,430 CLUT
  flushes/1,930 batches has per-VBlank spikes from a CLUT/parse/driver burst; the laptop's mean is already 19-20, so its
  p50 is at/over budget and its p99 is worse. `cpu_summary.py` reports p50/p95 only, so the p99 is not in the current
  logs.
- **Unknown:** the RTX 3060 laptop's exact per-VBlank split (`gif_parse`/`clut`/`batch_own`/`draw`/driver/`gpu_wait`/
  `present`); the license's `uber_batches`/shader compile on the laptop; the CPU/GPU clocks and thermal; the driver
  version; the in-game settings (resolution, Performance Mode); whether the owner's stutter is at 1x or another scale.

### 2.3 What would settle it

One license B-1 run on **each** machine (RTX 3060 laptop and 9060 XT), 1x, 60 Hz window (or headless with the pacer),
same build, warm shader cache, with **per-VBlank logs**:

- `[core2] exclusive ms/vblank`: `gif_parse`, `batch_own`, `translate`, `targets`, `texture`, `clut`, `draw`, `readback`,
  `targets`, `flush`, `vblank`; the `[core2] batch flushes/vblank` `clut`/`test`/`autoflush`/`capacity` split; the
  `clut_same_texture`;
- `[core2] specialised pipelines ... uber_batches`, `compile_ms`/`compile_max_ms`; the `[core2] shader cache` line;
- `[core2] gpu_wait ms/vblank by readback reason`; `[hw] transport` (`gif_ms`, `drain_wait_ms`, `read_fifo_ms`,
  `mtvu_wait_ms`); `[hw] profile present_us`; `[mtvu] EE wait`;
- the per-VBlank `wall`, `frame p50/p95/p99`, the frames >16.7/>20 ms, and the **per-VBlank trace** of the slow frames
  (`GT4_CORE2_SPIKE_MS`/`GT4_CORE2_SPIKE_LINES`, or the new CSV below);
- the CPU sampler on the GS worker (the `gif_parse`/`clut`/`record_draw`/driver split), and the CPU/GPU clocks/power.

**The settling answer:** if the laptop's `gif_parse + clut + batch_own + draw/driver` is about 18-20 ms and the GPU is
7-10 ms, it is the CPU license path; if `gpu_wait`/`present`/slot is the large term, it is a wait; if `uber_batches`/a
compile spike appears, it is the shader coverage; if the p50 is below 16.7 and only the p99 is over, it is the tail/
measurement. The per-VBlank stage split separates these; no existing log has it on the laptop.

**The counter/line to add:** a per-VBlank CSV (or a `[core2] frame` line) with
`vblank, wall, gs_stage, gif_parse, clut, clut_flushes, clut_same, uber, gpu_wait, slot_wait, present_us, frame_ms`, and a
scene tag (`GT4_BENCH_SCENE=license-b1`, `GT4_BENCH_RES=1x`, the GPU/driver/build) in `result.json`/the log; the
`cpu_summary.py` then reports p99, 1% low, the >16.7/>20 counts and the stutter ratio, not just p50/p95. The
`GT4_CORE2_SPIKE_MS`/`SPIKE_LINES` already exist; the stage fields and the scene tag are the additions.

## 3. Measurement methodology review

### 3.1 What the current method measures and what it hides

- `cpu_summary.py` reads the `[core2]`/`[perf]`/`[hw]` report lines over a VBlank window (default 600-VBlank lines) and
  prints **p50/p95** and averages (`gs_cpu`, `process_cpu`, `wall`, `gpu_busy`, `gpu_wait`, the `x_*` stages). It has no
  p99, no 1% low, no >16.7/>20 counts, no per-frame trace, no scene tag, no first-play/shader-compile flag, no GPU/CPU
  clock and no presentation-shown interval.
- The 600-VBlank averages smooth exactly the spikes the owner feels: a 19-20 ms mean can pass and a p99 of 25-30 ms still
  stutter; the 9060 XT's p50 10.58 can hide a 1,430-flush burst. The ledger itself learned this in IN-509 ("averages hid
  this; look VBlank by VBlank").
- The 10x/12x sweeps were **diagnostic** (fill extremes) but they shaped the last optimisation rounds; the streamer's and
  the license's realistic targets are 3x/Full HD and 6x/4K. The 12x work is not wrong, but it is not the acceptance.

### 3.2 Proposed acceptance metric

For every scene, resolution and mode:

- **60 fps:** game speed 100% (race clock/wall), p50 ≤ 16.7 ms, **p99 ≤ 16.7 ms**, **1% low ≥ 60 fps** (the 99th
  percentile of frame time ≤16.7), **frames >16.7 ms** and **>20 ms** as counts and ratios, **stutter ratio** (for
  example >20 ms frames per 1,000 VBlanks), max; the **presentation shown** intervals, not only the sent ones.
- The p95 stays as a secondary; the mean is context only.
- The identity gates (race clock, state, frames) remain per step; the metric is performance, not correctness.

### 3.5 CPU/GPU split

Per scene/resolution: the `[core2]` exclusive stages (`gif_parse`, `batch_own`, `translate`, `targets`, `texture`,

reason`, `draw_passes`, `fragments`, barriers, `[hw] transport`, `[hw] profile present_us`/`submit`, `[mtvu] EE wait`, the
`ee_dispatch`/`wall`, and the CPU sampler for the GS worker. The **GS worker CPU** and the **GPU busy** are separate
columns; a scene is CPU-bound when `gs_cpu` is near/over 16.7 and `gpu_busy` is low (the license: 8.92/1.04 on the 9060
XT; 19-20/7-10 on the laptop), GPU-bound when the reverse (12x).

### 3.6 Weak-GPU proxies

- **RTX 3060 laptop (i7-11800H):** the owner's weaker machine; the license TASK-171 data; use it for the CPU/front-end
  and the 1x/2x/3x; it is a **discrete** GPU (16 slots/64 batches).
- **GTX 1660 6 GB (the streamer's class):** a Turing 6 GB, much weaker than the 9060 XT; use it for **3x/Full HD** and
  the 6 GB VRAM/texture budget; no machine here, so a **9060 XT underclock/limit** (core/mem/power) is a proxy, not a
  substitute; the GTX 1660's driver (NVIDIA) and the 5600's CPU must be confirmed with the streamer.
- **Ryzen 5 5600 (6C) vs 5700X (8C):** the streamer's CPU; the license's GS worker/front end is single-thread dominated;
  the 5600's single-thread is close to the 5700X's, so the 5700X is a fair CPU proxy for the license; the 6C count matters
  for the EE/VU1/GS/driver threads, test if possible.
- **S23 Ultra:** the mobile tile-GPU target later; 1x/2x; the waits audit.

### 3.7 Run length, repetition, noise

- 2,000-4,000 VBlanks per scene (the license 2-3 laps, George V a full lap, the night 6,500-14,000), the 600-VBlank
  reports; **3 interleaved runs** per candidate (2+2 minimum), median and p99; the first 600 VBlanks excluded (warm-up);
  the shader cache warm (one run first; a cold-cache run measured separately); the machine quiet, the tools closed, the
  laptop on AC/performance, the clocks/temperature logged; the same build/driver/GPU; the frames identical; the scene tag
  in `result.json`.
- The **presentation** path: the shown intervals (`frametime.csv`), the `present_us`, the `presentations not shown`; a
  p99 of sent frames is not a p99 of shown frames.

- A **per-VBlank CSV** (the new line above) for the slow frames; the `>16.7` frames with the stage/CLUT/parse/uber/

- The **scene matrix** as a manifest (scene, track, mode, resolution, game, GPU, build) and the **3x/6x** defaults; the
  10x/12x runs marked diagnostic in the output.
