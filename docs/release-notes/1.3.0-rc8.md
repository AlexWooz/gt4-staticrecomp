# GT4Recomp 1.3.0-rc8 (test build)

**A test release candidate of 1.3.0 that adds CoreGS 2.0, our own hardware renderer, for Gran Turismo 4. A new install uses it when the graphics card supports it, and GSdx becomes an optional download.**

## What is new in rc8

- **CoreGS 2.0 (beta), Settings > Graphics > Renderer:**
  - MIT, inside the game executable, Vulkan only. Nothing is downloaded for it.
  - Both games: with CoreGS 2.0 chosen, Gran Turismo 4 (v2.00) and Spec II both run on it.
  - Choosing it does not remove GSdx; you can go back at any time.
- **The renderer defines the graphics options:**
  - Both: Render scale, Graphics card, Monitor, Resolution, Fullscreen, Vsync, Performance Mode, Anti-aliasing, custom textures.
  - GSdx only: API, Sharpening (CAS), Sharpening amount, Performance overlay.
  - CoreGS 2.0 only: Sharpening (FSR1): Off, Mild, Medium, Strong. Its Graphics card list holds only cards with Vulkan.
  - Vsync under CoreGS 2.0 offers On and Off; Fast is for GSdx, and a stored Fast draws as On.
- **Performance Mode on CoreGS 2.0:** off draws with full graphics precision. On hides the light flares, the sun glare and the road's sheen, draws small effect targets (up to 256 wide) at 1x and delays the flare visibility downloads. The road gets darker and the HUD car icon coarser.
- **Custom textures on CoreGS 2.0:** the same Textures folder and the same option as GSdx. Existing packs load unchanged (PCSX2-style names, PNG, subfolders). Tested with a 15,423-file HD HUD and UI pack.
- **Direct start:** starting the game executable without the launcher honours the CoreGS 2.0 choice through `game.ini`.
- **Compiling shaders (CoreGS 2.0):** Play now checks the shaders first. When they are not ready (the first time, after an update, a new graphics driver or another graphics card, or when the cache is gone) a window compiles them, then the game starts; when they are ready the game starts directly. One compile serves both games. The list holds 544 variants collected from both games, of which the card compiles those it can use (300 on the RX 9060 XT). A draw state the list does not hold still compiles during play. GSdx is unchanged: it compiles its own shaders during play.

## Frame pacing on CoreGS 2.0

Automated runs in a fullscreen window on an RX 9060 XT, Spec II George V Paris at 6x, 16:9, a race of 3,700 frames, against the previous build of this rc:

| | Before | Now |
|---|---|---|
| Graphics thread's processor time, Performance Mode off | 7.94 ms | 7.31 ms |
| Frames over 17.5 ms, Performance Mode off | 40 | 5 |
| Longest frame, Performance Mode off | 19.6 ms | 18.8 ms |
| Graphics thread's processor time, Performance Mode on | 7.78 ms | 7.24 ms |
| Longest frame, Performance Mode on | 17.5 ms | 17.6 ms |

- **Up to 16 submissions to the graphics card at a time** (8 before, and still 8 on integrated graphics), so the graphics thread no longer waits for the card along the frame (with Performance Mode off, the wait moves to the light flare read). Costs about 340 MB more of upload memory.
- **Frame rate (experimental), 60 or 30 FPS (CoreGS 2.0, Settings > Graphics, 60 by default).** At 30, races draw one frame in two and the simulation goes on at 60 Hz; menus stay at 60. Race clock equal at every VBlank and the state after a whole lap equal except for a few wheel values drawing writes, on both games; the frame shown is always the last one drawn (checked frame by frame). George V Paris at 12x on an RX 9060 XT, 144 Hz: 100% speed at 30 frames per second, intervals 33.0 to 33.7 ms (p1 to p99), against 76.9% speed at 46.1 without it.
- **Performance HUD (CoreGS 2.0, Settings > Graphics > Advanced, off by default).** A panel in the top right corner: graphics card, output size, render scale, refresh rate, FPS, frame time, the game's CPU and GPU use, memory, video memory and a live frame time graph. About 27 us of processor per presentation; no measurable change on the graphics thread.
- **Option selector.** Every dropdown and switch in Settings and the Achievements options is now the value between two arrows, in an endless loop, with the value sliding in from the side used. Only the Version row keeps its list. A renderer change animates the rows that come and go. Asynchronous GS is always on, and a stored "off" from an old version is ignored.
- **The game no longer waits for the light flare read, with Performance Mode off.** It waited about 9.5 ms per frame on George V Paris at 6x, so a heavy stretch lowered the frame rate. The game never reads that table: only the VU1 does, so the VU1 thread waits for it now, and the flares stay exact, frame for frame.
- **A shorter display queue under vsync.** At 60 FPS on a 60 Hz display, each refresh the display skips leaves one more frame waiting, for good. The renderer now watches the time from presentation to display and leaves one presentation out when it stays high. On the virtual 60 Hz test display, about 53 ms to about 40 ms across a lap. Displays over 60 Hz do not need it.
- **The presentation has its own queue on the graphics card, on cards that have a second one.** At 60 Hz, each presentation could hold back the rendering behind it (about 11 ms per frame in the showroom, on a game stream's virtual display; a real 60 Hz monitor was not tested). Now 0.01 ms, with no frame sent later than 18.2 ms in that race, at 2-6 ms more latency. On a 144 Hz monitor it costs nothing.
- **Recovery after a slow stretch is smoother:** frames no longer come in bursts of 9 ms intervals; the lost time comes back at about 1 ms per frame.
- **Every CoreGS 2.0 session writes `frametime.csv` beside its `game.log`:** when each frame was sent and when the display took it.
- A monitor faster than the game (such as 144 Hz) shows 60 frames per second as intervals of 14 and 21 ms: that comes from the monitor's fixed refresh, without adaptive sync.

## Lighter on weak graphics cards

Against the first build of this rc (candidate 362), Intel HD 620 at 2x, headless with shaders ready, GPU busy per VBlank:

| Scene and mode | Before | Now | Change |
|---|---|---|---|
| Day track, normal | 25.84 ms | 18.85 ms | -27% |
| Day track, Performance Mode | 25.74 ms | 16.75 ms | -35% |
| Night race, normal | 32.9 ms | 25.4 ms | -23% |
| Night race, Performance Mode | 33.0 ms | 22.7 ms | -31% |

RX 9060 XT at 12x, night race: 20.7 -> 19.1 ms (-8%).

- **Same picture, normal mode:** fragments that fail the depth or the alpha test leave before the pixel interlock; whole-target fills became clears; large full-screen passes run without the interlock on integrated GPUs; palette loads and repeated uploads are recognised instead of redone; draws that read nothing back go through colour attachments.
- **Compiled shaders are kept between sessions** in the user folder: a new executable needs a few sessions to prepare them, later ones start ready.
- **Videos behind the menus:** the MPEG decoder was rewritten with exact results; on the i5-7200U most frame intervals are now 16-17 ms.

## Fixes

- CoreGS 2.0 no longer refuses to start on a graphics card without the requested present mode (found on the HD 620, whose Vulkan has no mailbox): it takes the nearest mode the card has.

## Measurements

All on a Ryzen 7 5700X and an RX 9060 XT, headless night race at 3x, milliseconds per VBlank, three interleaved runs of each build. Single runs drift by a few percent.

- **Against the first beta candidate (313 -> 347, the same CPU work as this build, interleaved):** process CPU 22.0 -> 13.8, GS worker 7.76 -> 5.08, frame p50 10.9 -> 7.75.
- **Profile-guided optimisation and ThinLTO of the GS libraries, now in the release build:** GS worker 5.93 -> 5.14 (-13%), process CPU 16.48 -> 15.72 (-4.6%), wall 8.74 -> 8.33 (-4.7%), frame p50 8.72 -> 7.84. GPU time unchanged. Only the GS libraries are built this way; EE, VU and IOP code are not touched.
- **Graphics cards without pixel interlock (simulated with the interlock turned off):** GPU busy 49.05 -> 6.85, frame p50 46.3 -> 10.7, against 3.9 and about 7.8 with the interlock. Frames are identical to the interlock path.
- **Picture checks of this build against the reference frames:** 10 of 10 at 3x, 31 of 31 at 12x, 14 of 14 in the Arcade path, 28 of 28 in the track selection video.
- **With custom textures against no pack (3x, Arcade path):** GS worker +0.5 ms, frame p50 +0.3 ms, GPU +1%.
- **Compared with GSdx (owner's own play test):** about half the CPU; GSdx still uses a little less GPU.
- **A texture upload next to a drawn picture no longer waits for the GPU (Spec II, George V Paris at 6x, headless, three interleaved rounds):** GS thread 17.41 -> 14.04 ms per VBlank, 14.95 -> 12.25 in Performance Mode; GPU waits 4.86 -> 2.08 and 2.44 -> 0.39; frame median 20.03 -> 16.54 and 16.15 -> 12.97. 78 of 78 frames identical to the previous build.
- **Steadier frame times (same scene, same method):** GT4 draws one target every second VBlank, and each time the renderer dropped it and read six targets back. Change from one VBlank to the next 4.38 -> 0.44 ms, 3.87 -> 0.40 in Performance Mode; slowest 5% of VBlanks 21.87 -> 15.13, 17.35 -> 12.75. 117 of 117 frames identical to the previous build.
- **Race start, vsync and showroom, in a real window (Spec II, George V Paris at 6x, against the previous build):** racing without Performance Mode, VBlanks over 20 ms 29 -> 1 of 1000, mean 18.13 -> 16.79 ms; showroom GS thread 6.1 / 9.9 -> 6.0 / 6.0 ms on even and odd VBlanks, GPU waits 4.25 -> 1.40 ms; race start at 6x, headless, slowest 5% of VBlanks 19.7 -> 13.0 ms. Vsync now keeps three images, which can add up to one frame of latency. Frames: 1x, 3x and 6x identical; at 12x one of 31 differs in 2 pixels by at most 8 of 255.

## Install or test

- **Installer:** run `GT4Recomp-Setup-1.3.0-rc8.exe`. It keeps existing settings, saves and replays.
- **Portable:** unpack `GT4Recomp-1.3.0-rc8-portable.zip` anywhere. Settings, saves and data stay inside the folder.
- **Disc images:** you need your own: Gran Turismo 4 (USA, v2.00), and your own Spec II 1.10 image for the mod. GT4Recomp ships no copyrighted game files.

## Known issues and limitations in this test build

- **Weak graphics cards are being verified.** The test on the i5-7200U / HD 620 laptop decides the items below.
- **Hardware raster path not included.** Measured first: the exact path reaches only about 4% of the drawn area beyond the existing fast fills, 38-44% of the area is blended (the GPU's blending rounds differently from the GS), and on the test card hardware blending costs the same as the current path. It is left out unless the laptop test shows it matters.
- **Without pixel interlock** the GPU cost is still higher than with it (6.85 ms against 3.9 ms on the test card). This path was tested only by turning the interlock off on a card that has it.
- **Custom textures:** mipmaps sample the base image only; compressed DDS and zip packs are refused; the older Format G names are not read; palettes written by the GPU are not replaced.
- **Spec II on CoreGS 2.0** was checked headless at 3x in Arcade races (C.S. Route 5, Costa di Amalfi, the start of George V Paris), in both Performance Mode settings. GT Mode and a window are not checked yet.
- **Graphics settings baseline:** the known GS settings test expectations from rc6 remain documented as baseline behavior.
- **Not in this build:** fractional render scales.
- **Frame rate at 30:** the speed number on the race display can read up to about 3 mph differently, because the game smooths it per frame drawn (no effect on the race). Works in 480p, which the launcher always uses. Split screen was not tested.
- RetroAchievements, controller curves and everything else are unchanged from rc7; the Spec II game program is rebuilt with the renderer.

## Requirements

Windows 10 or 11, 64-bit, a processor with SSE4.1. CoreGS 2.0 needs a graphics card with Vulkan 1.2.
