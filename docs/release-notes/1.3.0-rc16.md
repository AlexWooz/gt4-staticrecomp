# GT4Recomp 1.3.0-rc16

> **Test build for the owner.** This is the TASK-204 and TASK-206 test build of the 1.3.0 line: CoreGS 2.0 no longer
> compiles a pipeline during play, and the shader preparation now covers the render scale the session will use. It is
> **Gran Turismo 4 v2.00 only** (no Spec II), and it is a plain build (no PGO, no ThinLTO), not the rc15 fast build.
> The scale expansion is new: if something looks or behaves wrong, send us the launcher's `data\logs` folder and the
> session's `game.log`. The draft is never offered by the launcher's update channels.

**CoreGS 2.0 stops compiling graphics pipelines in the middle of a race: an unknown shader variant is drawn with the
general pipeline (the same pixels) and recorded, and the next Play's preparation compiles it. The preparation now expands
the variant list over the session's render scale, so a 4x session starts with the keys it is going to ask for: on the
recorded Paris scene, 0 deferred keys and the identical frames, with the 1.91 ms per VBlank the fallback used to cost
gone.**

## New

- **The shader preparation covers the session's render scale (TASK-206).** The render scale is part of the CoreGS 2.0
  pipeline key: a key is a draw state *at a scale*, so a 4x session asks for a parallel set of every state it touches.
  `--prepare-shaders` now takes `--prepare-scale N` (N is the CoreGS 2.0 internal multiplier, `GT4_HW_SCALE`, 1 to 12,
  never the Render scale percentage), and `variants_to_prepare` expands every shipped and recorded key over it:

  - the **1x shape** of the key: the sampled image at 1x (the atlas, a replacement image, a mipmapped game texture, a 1x
    effect target);
  - and, when the key samples a texture image and the frame is above 1x, the **target shape**: the same image drawn at
    the scale, the main frame included. Push bits 28 and 30 (depth from position, fine dither) follow the frame: set above
    1x where the key keeps them and cleared at 1x.

  A key recorded at another scale is not added as it is (no session at this scale can ask for it); its state is kept
  through its 1x shape and returns at any scale by expansion. The expansion runs before the card/feature filters, the
  quarantine and the 2048-key cap, and the expanded list is what the preparation writes to `variants.bin`, so the session
  queues exactly what was prepared. No shader, key-format or specialisation change; the shipped corpus
  (`core2_known_variants.inc`) is untouched.
- **The launcher passes the scale it will use (TASK-206).** The launcher resolves the CoreGS 2.0 multiplier from the
  display and the Render scale exactly as its session does (`launch::coregs20_scale`, the same number it sends as
  `GT4_HW_SCALE`) and passes it to the preparation, so there is no guess and no second source of truth. The preparation
  prints `shaders scale N` and `shaders added K`, logs `N variants for Sx (R recorded, K added for the scale)`, and the
  launcher logs `shaders: N keys prepared at Sx`. Without the option the preparation keeps its old behaviour, scale 1, and
  says so in its log.
- **The preparation stamp carries the scale (TASK-206).** `PreparedStamp` (magic `GT4PREP2`) now holds the scale next to
  the variant count and hash. A session whose `GT4_HW_SCALE` does not match the stamp uses no prepared list: it compiles
  nothing, draws with the general pipeline (the same pixels) and records its keys for the next preparation. Changing the
  Render scale is therefore a documented new preparation, not a silent mismatch.

## Fixes

- **CoreGS 2.0 never compiles a pipeline during play (TASK-204).** A player on rc15 at 4x met `0xC0000005` inside a
  pipeline compile on the preparation thread 20 minutes into a lap (`compile_max_ms` 1,047.9). The in-play compile had no
  retry loop and no quarantine: an unknown key now enters the session's recorded list exactly once, returns no pipeline,
  and its batch draws with the general (uber) pipeline, which produces the same pixels. The session start recreates only
  the pipelines a matching `prepared.bin` vouches for, from the disk cache. `GT4_CORE2_INGAME_COMPILE=1` restores the old
  compile path for an A/B; a developer run without a shader cache keeps compiling.
- **Recorded keys make the next Play prepare again (TASK-204).** `prepared.bin` did not hash `variants.bin`, so after a
  session recorded new keys the preparation still reported itself ready and the game compiled them itself. The stamp now
  carries the FNV-1a hash and the count of `variants.bin`; the preparation writes the stamp of the list it compiled, so
  new keys always ask for a new preparation. A missing, empty or damaged `variants.bin` has a defined stamp value, so a
  bad stamp only asks for a preparation.
- **One strike in play quarantines a key (TASK-204).** A key left in `compiling.bin` at a game start is quarantined at
  once, so the same driver crash cannot repeat every start. The launcher's preparation keeps its two strikes
  (TASK-170c), and a quarantined key is never recorded again (no preparation loop).
- **The launcher's preparation logs name the recorded keys (TASK-204).** The preparation prints `shaders recorded R` and
  the launcher logs `shaders: R recorded keys compiled`; the game's `[core2] specialised pipelines=` line gained
  `deferred=N deferred_uber_batches=M`.

## Performance

- **A 4x session prepared at 4x stops paying the fallback (TASK-206).** Headless George V Paris, B-Spec, 4x, 2,400
  VBlanks of race, four frame dumps (VBlank 4800/5400/6000/6600). The deferred run (fresh cache) recorded 75 keys, created
  0 pipelines and drew 2,645,167 batches with the general pipeline. `--prepare-shaders --prepare-scale 4` then compiled
  **175 variants in 130.6 ms** (max 1.2 ms per variant), 0 failed, 0 quarantined, `shaders added 39`. The prepared run had
  **0 deferred keys, 0 deferral-caused uber batches**, 175 pipelines recreated from the disk cache, and **4 of 4 frames
  identical** (0 differing pixels). Over the race's four 600-VBlank intervals, `gpu_busy` was **3.78 against 5.71 ms** per
  VBlank (prepared against deferred) and wall time **8.76 against 8.96 ms**, which is the 1.91 ms per VBlank (+50%) the
  fallback cost in TASK-205. The residual is 13 general-pipeline batches in the first moments, before the worker finished
  recreating the pipelines; they are not deferrals.
- **The variant list on this card (RX 9060 XT, before the card filters).** The 544-key corpus becomes 255 distinct keys at
  1x (544 written) and 336 at 2x/4x/6x (795 written, 251 keys with both shapes; the count is the same above 1x because the
  shape replaces the scale with 1 or S). After the card's plain/feature filters, **175 keys at 4x** (136 1x shapes plus
  39 targets) where it kept 300 before, and **142 at 1x** with a session's six recorded keys. Fewer keys, better coverage:
  a key recorded at another scale could never be asked at this one.
- **A smaller 1x preparation.** At 1x the preparation no longer compiles the 2x/3x/6x keys as they are, so it is shorter
  and the cache is smaller; nothing is lost, because those keys cannot be asked at 1x.

## The same game

- **Pixels, TASK-204:** headless v2.00 night race at 1x, 11,500 VBlanks, dumps from VBlank 6500 every 600. The default
  run (0 pipelines, 97 keys deferred, 3,153,803 general-pipeline batches caused by them) and the run with
  `GT4_CORE2_INGAME_COMPILE=1` (97 pipelines, 35,498.9 ms of driver compile, max 503.1 ms) produced **9 of 9 identical
  frames** (SHA-256 per frame). A run after a preparation recreated 328 variants in 256.5 ms and matched 9 of 9 again; the
  preparation that followed compiled the 3 keys the corpus lacked, and a fourth run recreated 331 in 349.3 ms with 0
  deferred and 9 of 9 identical.
- **Pixels, TASK-206:** the 4x gate above, **4 of 4 identical frames** between the deferred and the prepared run.
- **Game logic:** no physics, timing, AI, save or game-logic change. The work is a pipeline-compile policy and a
  preparation-time list transformation; the shipped shader corpus is untouched.

## Known issues

- **v2.00 only.** This test build ships no Spec II program: the Spec II executable built from the same source exists for
  the headless 4x gate and is not distributed (it has no pinned distribution). Installing this build replaces the game
  folder, so an installed Spec II is not available again until a build that ships it.
- **Plain build.** No PGO and no ThinLTO: the code is the TASK-206 source built plainly, so race performance is not the
  optimised rc15 level. It is for testing the new compile policy and the scale expansion.
- **TASK-201 is not included** (owner: later). rc15 already has TASK-199's info-card layer; the extra check of the next
  row's "(i)" icon and label over an open card is not in this build.
- **The first Play after a Render scale change prepares again.** The cache prepared for the old scale is refused on
  purpose (the scale is in the stamp): that session draws the unseen keys with the general pipeline (the same pixels) and
  records them; the next Play prepares at the new scale. The same happens once after this update.
- **A failed or skipped preparation** leaves every variant on the general pipeline (the same pixels, more fragment cost)
  until the next Play's preparation. A quarantined variant stays there on this card and driver; the way back is deleting
  the shader cache's `quarantine.bin` (the support log lists it).
- **Photo mode on slower graphics cards (CoreGS 2.0):** each picture still waits for the graphics card twice, so frame
  times can be uneven (TASK-162). Unchanged.
- **2x/3x/6x/12x sessions** are covered by the list fixture, not by pixels in game; the headless gate is the 4x Paris
  scene. The owner's in-game test covers the other scales.

## Install or update

- **From an earlier 1.3.0 build:** run the installer below. Settings, saves and replays are kept. Installing this test
  build removes `gt4-spec2.exe` from the game folder (v2.00 only, see above).
- **Installer:** run `GT4Recomp-Setup-1.3.0-rc16.exe`.
- **Portable:** unpack `GT4Recomp-1.3.0-rc16-portable.zip` anywhere. Settings, saves and data stay inside the folder.
- **After the update,** the first Play may prepare CoreGS 2.0's shaders once, as after every update; the preparation now
  uses the Render scale the launcher will pass to the game.
- **Disc images:** you need your own Gran Turismo 4 (USA, v2.00). GT4Recomp ships no copyrighted game files.

## Requirements

Windows 10 or 11, 64-bit, a processor with SSE4.1. CoreGS 2.0 needs a graphics card with Vulkan 1.2.
