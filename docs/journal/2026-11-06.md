- **TASK-192: the G27's slow pull to the centre is GT4's own spring, off by default now.** Owner report on rc15: "the
  steering is heavy and not natural; from the moment the game opens, the wheel keeps slowly coming back to the centre, all
  the time" (he set GT4's own force feedback to Weak and the launcher's damping to 0%, and the pull stayed). Branch
  `task/192-ffb-centering` from `release/1.3.0-rc15` at 3df155c4; one writer; no PR, no merge.
  - **Measured, not guessed:** the rc15 v2.00 and Spec II builds headless with the virtual wheel (`GT4_DFP=1 GT4_DFP_TRACE=1`,
    the census and `dfp-forces.csv`), through the menus and the bench drives `licenca-b1` (v2.00 licence test, 3,514
    VBlanks) and `el-capitan` (Spec II time trial, 10,757). The game's racing force depends on the wheel angle, and a
    headless run without a host wheel reports a centred wheel, so a new check `GT4_DFP_TEST_STEER=<percent>` sweeps the
    virtual wheel (a triangle over 600 reports, about 6 s) to see the forces off centre.
  - **What GT4 asks for:** at boot `F3` (stop all), `F4` twice (default spring on), `F5` (off, and it stays off), `F8 03`
    (900 degrees). In the menus a high-resolution spring (`21 0B 7F 7F 77 00 80`, slot 1 or 2): k = 7 on both sides
    (7/15 = 0.47), clip 0x80 (0.5), centred, no dead band, stopped with `23 0B` before a drive. While driving: no spring and
    no damper, friction on slot 1 (`21 0E 80 FF 20`, coefficient 0x80, clip 0x20 = 0.125) and the variable force
    (`11 08 <L1> 80 00 00 00`) about 100 times a second, its level following the wheel angle (mean level 0x2D at the left of
    the range, 0x80 at the centre, 0xCA at the right): GT4's self-aligning torque, sent as a constant force.
  - **Cause:** the game's own centring spring, played exactly as the game asked. The decoder and the planner were right in
    kind (coefficients, clip and centre match GT4's bytes), and the DFP default spring was already off; but the spring is a
    centring force and the owner does not want it. During a drive there is no spring at all, so the aligning force he calls
    "impeccable" stays. The damper floor in the `wheel.toml` of his logged session was 15% (the launcher screen at 11:46
    shows Amortecimento 15%), which is what made the pull slow and the steering heavy; his 0% test came after that log.
  - **Fix:** `[ffb] centering_spring = "off" | "game"`, default **off** (owner: "I think it has to be disabled"). `off`
    plans neither the game's spring effects nor the DFP default spring; `game` is the old behaviour; the racing force, the
    damper, the friction and GT4's Strong/Weak scaling are untouched. A 1.2.x file's amount or boolean still parses (nonzero
    = `game`), and the "centring" spelling parses too, so old files keep loading.
  - **For the next report:** a `[dfp] census` of the session's force commands at the end of every session in `game.log`
    without the trace switch (each command and type with its count and latest bytes, plus the last decoded force set), and
    the `[wheel] force feedback summary` line now ends with `centering spring off|game`. `dfp-forces.csv` records the
    steering the game last saw, not the host wheel's.
  - **Checks:** `native_usb_dfp` feeds GT4's exact command bytes and checks the decoded spring, its stop, the friction and the
    racing force; `native_wheel` checks the plan with the setting off and on (nothing else changes), the key's tokens and
    spellings, the refusals, the round trip and the summary line; the haptics-thread update count follows the spring no
    longer changing on the first force set. CTest 318 of 319 on the v2.00 build (`hw_replace_q07_pcsx2_dumps` skipped, as in
    rc15), Python 804 (57 skipped).
  - **Launcher row (follow-up):** Settings > Wheel > Force feedback > Centring spring (Off / Game). `gt4l-core`'s
    `wheel.rs` refuses unknown `[ffb]` keys, so it must learn `centering_spring` before the row can ship; until then a
    hand-edited file with the key is refused by the launcher (the game loads it).

- **TASK-188: saves on a PC whose install and save library are on different drives (issue #208, rc15).** Reported by Yenemay
  (1.3.0-rc14, Spec II, Windows 10, Russian UI): pressing Delete in the Saves page did nothing, deleting
  `AppData\Roaming\GT4Recomp\games\spec2\Saves` by hand brought the save back at the next start, and New save failed with
  `F:\gt4spec2\GT4Recomp\data\games\spec2\runtime\card.ps2: ... (os error 17)`. Branch `task/188-cross-drive-saves` from
  `release/1.3.0-rc15` at 110cacad; one writer; no PR, no release.
  - **Cause (Confirmed from the code, then reproduced by tests):** the runtime card lives in the install's data folder and the
    save library with its card backups in `%APPDATA%\GT4Recomp`, so on that PC they are on `F:` and `C:`. The card was parked
    with `fs::rename` (delete: `-before-delete.ps2`, New save: `-before-new-save.ps2`), which Windows refuses across volumes
    (`ERROR_NOT_SAME_DEVICE`, os error 17). Delete therefore stopped before the Recycle Bin call, New save failed with that
    text, and the card left on `F:` was harvested again at the next Play, which is why a hand-deleted save returned.
  - **Fix:** new `gt4l_core::moves` (`move_path`, `move_path_with`, `MoveOps`, `is_cross_device`): rename when both places are on
    one volume (atomic, replaces the target as before), and across volumes a copy checked file by file (size and SHA-256),
    placed through a staging name on the destination's volume, then the source removed; a bad copy keeps the source and
    removes only the half copy. Used by `park_runtime_card` (delete and New save) and by the pre-1.0 library migration's park
    (`migration::migrate` now takes a `Mover`; the launcher passes `moves::move_path`).
  - **Audit:** 51 `fs::rename` sites in `launcher/crates`, 45 in product code: 42 are inside one folder or already
    cross-volume-safe (`relocate`, `games_layout`, the installer's own swap), and the 3 that could cross volumes (delete park,
    New save park, migration park) now use the helper. Full table in the TASK-188 hand-off.
  - **Tests:** 8 helper unit tests (same-volume rename never copies; file and folder across volumes; a truncated copy refused;
    a target replaced; a missing destination folder; a missing source), 3 new flow tests in `gt4l-tauri` with the card and the
    library under different roots and a rename reporting another volume (delete clears the card and the next card has no save;
    New save parks the card and keeps the old save in `Save 01`; harvest and a rebuilt card across roots), and a
    `gt4saves` migration test that the park goes through the mover and keeps the data when it refuses. `cargo test --workspace`
    769 passed (9 ignored); focus checks 358/358 (en-US) and 365/365 (pt-BR), nav-test 260/260, locale keys 925 in both.
  - **Build:** games unchanged (slice411, `private/slice411-dist-130-rc15b`); launchers labelled rc15 (installer build
