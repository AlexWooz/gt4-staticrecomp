- **Item 1, the capability log (C).** `DeviceProfile` gained `OrderingCapabilities`: rasterization-order attachment access
  (EXT and ARM spellings) with the colour/depth/stencil bits, `VK_KHR_dynamic_rendering_local_read`, the two attachment
  feedback-loop extensions, `VK_EXT_shader_tile_image` with its three read bits, and the four fragment-shader-interlock
  bits. The probe fills it from the extension list and from feature structs chained only where their extension exists, and
  game.log prints one `[hw] ordering:` line on every platform. The device is created with
  `rasterizationOrderColorAttachmentAccess` (and depth/stencil where offered) so the path can be used where it exists.
  This desktop (RX 9060 XT) has none of the ordering bits but does report dynamic-rendering local read, attachment
  feedback loop layout and the pixel interlock; the S23's Adreno 740 has none of them, which is why its per-primitive
  barriers cannot be replaced by hardware order (C, its own `vkjson` list).
- **Item 2, `GT4_CORE2_RASTER_ORDER` (C for the decision and the flags).** Auto-on where the device was created with the
  colour feature; the colour-attachment subpass and its pipelines carry the ordering flags. It removes no barrier today
  and that is expected: the attachment path already pays none (one draw per batch, fixed-function order), and the 565-1,070
  "may share" barriers belong to the storage path, whose fragment stage reads the words it writes. Ordering those reads
  needs an attachment read in the same subpass, i.e. a layout extension plus this ordering bit. Pinned by the
  mocked-capability fixture (`hw_device_profile`) and by `static_assert`s that tie the plain flag constants to the Vulkan
  enum values; this desktop has no such device, so the Vulkan objects cannot be created here, which the section says.
- **Item 3, `GT4_CORE2_TIGHT_OVERLAP` (C).** The "may share a pixel" test of the no-interlock path is now an output-pixel
  test (`core2_overlap.hpp`): the box of pixels the primitive can cover on the raster grid, clipped by its own scissor, and
  for two axis-aligned right triangles a closed-form per-row interval test with the top-left fill rule (a shared edge or
  diagonal is not a shared pixel). General triangles keep IN-471's separating-edge test on top of the box. Hong Kong 2x
  with `GT4_HW_INTERLOCK=0`: fragment barriers **1,103.22 -> 830.45 per VBlank (-24.7%)**, all of it the "may share" row;
  Motegi 2x **593.39 -> 498.39 (-16.0%)**; full barriers and render passes unchanged (565.73 / 52.31 and 239.78 / 46.71);
  draw calls 1,147 -> 953 and 1,007 -> 794 (primitives that need no barrier now merge). Indicative presenting run: GPU busy
  4.36/4.64 -> 3.96/4.18 ms. Identity: the four section-3 flare hashes reproduced (`2f4c1cc9f174d00e`, `61109e8f3143264a`,
  `7bf932fbb8799965`, and Motegi without interlock `7bf932fbb8799965`), and 12 of 12 composed frame dumps identical off
  against on (menu VBlanks 1497-1500, Hong Kong and Motegi races 5397-5400).
- **A bug worth remembering (C).** The first version called a triangle a "right triangle" when three of its box corners
  were *present*, without checking that its vertices were those corners: a slanted triangle with a vertex in the middle of
  an edge of its box passed, the row test then used the wrong geometry, and the Hong Kong count doubled (2,186). The
  classification now requires every vertex to be a corner and the three to be distinct; the fixture's brute force is what
  pins it.
- **Fixtures (C).** `hw_core2_overlap` (new, CPU only): 7,015 pairs at 1x/2x/3x/12x against brute-force pixel coverage,
  0 pairs where the test says "no shared pixel" and brute force finds one; the two halves of a sprite, two sprites side by
  side and two stacked are all "no", a scissor that removes a primitive leaves an empty box; 225 of 2,250 "share" answers
  on random boxes are false positives (cost, never correctness). `hw_device_profile` gained the mocked capability cases and
  the flag mapping.
- **Item 4, the attachment loads and stores: audited, nothing shipped (C).** The storage pass has no attachments at all, so
  no load/store op exists there. The attachment passes use LOAD/STORE on the frame (content persists between passes), bind
  depth only when the batch writes depth, and already use `DONT_CARE` for stencil; the render area is the whole
  attachment, so narrowing it is not exact. The one exact reduction found is to fold a whole-image clear into the next
  attachment pass's `loadOp = CLEAR` (one tile-memory clear instead of a full-image write plus a full-image load); it needs
  a deferred clear with its hazard proof and is a step of its own, so the 6.8/6.4 clear pass ends per VBlank are unchanged.
- **Full CTest, serial:** 322 tests, **100% passed, 0 failed**, 1 skipped (`hw_replace_q07_pcsx2_dumps`), 504.2 s; the new

- **For Android:** `GT4_CORE2_TIGHT_OVERLAP=1` (default off; exact, -25%/-16% fragment barriers on the desktop's

## The 3x `gif` growth (the brief's last question)

The brief's 3x observation (the GS thread's `gif` at 28.6 ms per VBlank on the phone) does not reproduce on the desktop,
and that is itself the useful answer: the same Hong Kong race at 2x and 3x has **every CPU-side category identical**
(`gif` 6.75 -> 6.80, `batch` 3.36 -> 3.36, `upload` 1.39 -> 1.42, `draw` 1.01 -> 1.00, the same 130 uploads, 368 CLUT
passes, 52 GLM calls and 264 pages), while `gpu_busy` grows 2.87 -> 3.84 ms and `gpu_draw_passes` 0.99 -> 1.67 ms, and the
only CPU number that follows the scale is `gpu_wait` (0.33 -> 0.60 ms). So the scale reaches the GS thread through
*waiting*, not through scaled CPU work; on the phone, where the GPU is further behind at 3x, the same blocking points (they
sit inside the `gif` phase) turn into the 28.6 ms reported. No code change was made for it: the lever is
`GT4_CORE2_SUBMIT_EVERY` (the phone measured +11.6% VBlanks/s at 128) plus the per-pass cost this task attacks, and the
phone's own `gpu_wait`/`submit` counters in the 600-VBlank line decide the rest.
