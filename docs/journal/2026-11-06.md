## TASK-180b: Spec II's black picture and 3.2 s guest frames on Android (the S7b IOP rule was never wired there)

The other agent saw Spec II black after 100 s in the emulator with `gif bytes/frame: path1=0 path2=0 path3=0` and
`run_due_events=3248 ms/frame`, and guessed the ARM translation. It is not the translation: the Android build of
`libgt4spec2.so` never had the TASK-100 S7b asynchronous FILEIO server.

**Reproduction (emulator-5554, the test5 APK, Spec II 1.10 PT-BR `fe8b51cf…` from this PC, the launcher's own Play
arguments).** The launcher's own Play could not be driven in the emulator (see below), so the game was started with the
same Activity, arguments and environment (`GAME=spec2`, `libgt4spec2.so`, the derived ELF, `--disc` as the content URI the
launcher stores, the launch plan's `GT4_*` list):
- 1.0 guest VBlank/s, `EE frame wall=1945 ms`, `run_due_events=1903 ms`, `ee_dispatch=16.8 ms`, `iop_run=12.8 ms`,
  `path1=path2=path3=0` GIF bytes: the guest never drew and the frames were ~1 s apart.
- Without a window (`--window` removed): 58,800 guest VBlanks in 25 s. The guest and the language emulator are fine; the
  wait is around the VBlank.
- simpleperf (`--trace-offcpu`): 79% of the process CPU in the GS worker inside `goldfish_pipe_read_write` (gfxstream's
  transport), the EE thread blocked in a futex, and ~97,000 read syscalls/s returning ~1.2 bytes each.
- `[gs] vblank 10: flush 0.28 ms, next_frame 0.01 ms, present 959.24 ms` (new `GT4_GS_PRESENT_LOG`): a present costs
  about a second in this emulator (lavapipe behind gfxstream at 2400x1080).
- The F8 breakdown (new `[frame] run loop` fields): `run_due_events=1903 (worker pump=… sif pump=… events=… vblank=…)`;
  with `GT4_MTVU=0`, `GT4_PACING_NO_WAIT=1`, `GT4_HW_GS_THREAD=0` and `GT4_HW_SCALE=1` the picture stayed black, so none of
  those was the cause.

**Cause (Confirmed).** The PC Spec II log of the same build line prints
`[sif] DNAS310.IMG is a Sony IOP reboot image (LOADFILE 3100): asynchronous FILEIO server`, then
`[fileio] devctl dev9x: 0x4401`, and the boot continues through SMAP/PPP/PPPOE/MSIFRPC/LIBPDI/… to the menus. The Android
log prints neither line and stops after `[loadfile] cdrom0:\IRX\INETCTL.IRX;1`: the game's fileio thread waits for the
`dev9x:` devctl completion for ever, so the network init never finishes and nothing is drawn.
`native/CMakeLists.txt` (Windows) has spliced the capsule's `iop/sif.cpp` since TASK-100 S7b (`GT4_SPEC2_CAPSULE_RE`);
`android/native/CMakeLists.txt` never did, so the shipped `libgt4spec2.so` ran the donor's synchronous FILEIO server, whose
devctl returns -1 without the 0x80000011 interrupt packet. Binary control: `b"asynchronous FILEIO server"` appears 0 times
in the test5 `libgt4spec2.so` and 1 time in a build with the splice.

**Fix.** `android/native/CMakeLists.txt` now requires a Spec II runtime capsule with `sif.cpp`, verifies it against the
capsule pin and compiles it in place of the donor's `iop/sif.cpp` (the same rule as the Windows build). A Spec II configure
without such a capsule fails with a message naming the file.

**After the fix.** The game passes the network init and draws the SCEA and Polyphony Digital screens (screenshots in
`build/evidence/t180b/`): `gif bytes/frame` goes from 0 to 313,904 (7 records) and the guest runs at 24-34 VBlanks/s at
2x. What it does **not** do is leave those screens: the seven records repeat byte for byte for as long as the runs lasted
(up to 15 min, with a second, stale emulator killed and 24 VBlanks/s measured again), so this is a second Android-only
stall after the S7b one, not isolated yet. The owner's S23 log shows the same 313,904 B / 7-record phase while booting
v2.00 and then moves on (253,893 / 5.7 records, 121,276, 2,339, 74,750 …), so the phase itself is normal and this game
stops inside it. The emulator's software Vulkan makes the picture expensive (100 ms of GPU for a 306 KiB frame, ~1 s
presents while the pipelines warm up, ~97,000 1-byte reads/s in the guest Vulkan driver), which is why 15 min is only a
few thousand frames.

**Instrumentation kept.** Five new F8 categories (`runloop_mtvu_pump`, `runloop_sif_pump`, `runloop_events`,
`vblank_action`) printed in the `[frame] run loop` line, a `gs_drain` scope around the journal drain inside
`mtvu::pump()`, and `GT4_GS_PRESENT_LOG` (per-VBlank flush/next_frame/present times). The run-loop categories read zero
unless the runtime capsule is made with `scripts/prepare_perf_runtime.py --runloop-breakdown` (diagnostic capsule
`slice453-t180b-runloop-runtime`, pinned in `docs/inputs`).

**Gates.** Windows build of the shared code (`private/slice454-t180b-win-build`, v2.00 production, slice262 capsules):
CTest 324/324 (1 skipped: `hw_replace_q07_pcsx2_dumps`), Python 802 OK (48 skipped). The Android v2.00 library is
untouched by the CMake change (the block is `GT4_TARGET STREQUAL "spec2"` only).

**Not done.** The launcher's own Play could not be used: the launcher's first-start dialog ignores taps in the emulator
(its JOGAR/CANCELAR buttons take no touch), the Settings > Jogos page kills the emulator three times in a row, and the
install hash of 3.7 GB through SAF was not repeated; the game was started with the launcher's exact launch contract
instead. Spec II still does not reach its title screen inside the emulator's test window: it draws the publisher screens
and then repeats the same seven GIF records at 24-34 VBlanks/s for as long as the runs lasted (a second, Android-only
stall after this fix, not isolated), and the emulator's software Vulkan makes each frame 40-50 ms.

## TASK-180b, second pass: the Android build also never defined GT4_TARGET_SPEC2

After the S7b fix Spec II drew the SCEA and Polyphony screens and then repeated the same seven GIF records (313,904 B,
7.0 records) for as long as a run lasted. Comparing the two build files line by line found the reason.

**The Windows/Android splice table** (`native/CMakeLists.txt` against `android/native/CMakeLists.txt`):

| Item | Windows | Android (test5) | Matters for Spec II's boot |
|---|---|---|---|
| `GT4_TARGET_SPEC2` (the Spec II row of `native/game_target.hpp`) | defined when `GT4_TARGET=spec2` | **not defined** | **Yes: it was the stall** |
| Spec II runtime capsule `sif.cpp` (TASK-100 S7b) | spliced for a slice27x capsule | **not spliced** | **Yes (first stall, fixed in e5d8ac0d)** |
| memory card capsule `sio2.cpp` | spliced, pinned | spliced, pinned | yes, identical |
| IPU capsule `ipu.cpp` | spliced, pinned | spliced, pinned | yes, identical |
| SPU2 capsule `spu2.cpp` | spliced, pinned | spliced, pinned | yes, identical |
| license guard `dispatch.cpp`, `kernel.cpp`, `cdvdfsv.cpp` | spliced, pinned | spliced, pinned | yes, identical |
| frame-cost capsule (`system`, `vif`, `vu_micro`, `gif`, `memory`, `hw`, `dmac`) | spliced, pinned | spliced, pinned | yes, identical |
| VU1 AOT generated table | `GT4_VU1_GENERATED_DIR` | same | yes, identical |
| VU0 AOT | generated table or a `GT4_VU0_IMAGE_FILE` image | generated table only (both Android builds use one) | yes, same result |
| USB capsule `iop/hw.cpp` (DFP wheel) | optional, spliced | not built | no (no wheel on Android; the donor stub answers) |
| `GT4_MEMCARD_FLUSH_OVERLAY` | defined with the capsule | defined always | yes, same effect |
| `--prepare-shaders` (`GT4_HW_SHADER_PREPARE`) | Windows argument | Android has its own `prepare_shaders_main()` | no |
| observation capsule (`GT4_SHAPE_RUNTIME_SOURCE`) | optional | not built | no (debug feature) |
| `PS2_GPU`, `GT4_GS_STREAM_HW`, `GT4_GS_STREAM_CLIENT` | defined | defined | yes, identical |
| EE code | a pinned `ps2game.lib` per profile | the units compiled from a directory | yes, same code |
| GS backend | donor `gpu.cpp` + `native_vulkan.cpp` | `gpu_unavailable.cpp` + CoreGS 2.0 | by design |
| RetroAchievements, `standalone.cpp`, the GS process | Windows-only | not built | no (`GT4_RA_ENABLED=0` on Android) |

**Cause (Confirmed).** `native/game_target.hpp` keeps one table of guest addresses per target and selects it with
`GT4_TARGET_SPEC2`; `native/CMakeLists.txt` has set that definition since TASK-100 S3, the Android build never did. The
Spec II library therefore ran the **v2.00** addresses of every host hook. The symptom is visible in the boot log: the
game-data pointer line read `0x00000000 -> 0xFFB30018 at vblank 1` on Android against the PC's
`0x00000000 -> 0x009BD690 at vblank 12`, so the 16:9 hold, the 480p hold and the display-request reader either found
nothing or read a lookalike object, and the game stopped after the publisher screens. The hooks are range-guarded, so
nothing was corrupted; the Spec II display state simply never became what the game waits for.

**Fix.** `android/native/CMakeLists.txt` now adds `GT4_TARGET_SPEC2` when `GT4_TARGET=spec2`, exactly like the Windows
build, right after the existing check that only `v200` and `spec2` are accepted (a third target fails the configure).

**Proof (emulator-5554, test5 APK with the new library, Spec II 1.10 PT-BR):**
- `[display] game-data pointer 0x00000000 -> 0x009BD910 at vblank 12 (moves 0)` and
  `[display] GT4_FORCE_480P: race display index 0 (normal) set to 1 (480p) at guest 0x009BF6A8 (owner 0x009BD910)`, the
  same shape as the PC's line (its addresses differ by 0x280, a platform allocation difference).
- The seven-record loop ends: `313,904 B / 7.0 records` -> `282,773 / 6.3` -> `167,951 / 28.2` -> 0, the game plays its
  opening movie at 20-24 VBlanks/s and reaches its title screen: **GRAN TURISMO 4 spec-II** with `Modo Arcade` / `Modo
  Gran Turismo`, `©2006 SCE & Polyphony Digital Inc. Tradução Ver. 1.3 por Kamikaze496`, `v1.10` top left
  (`build/evidence/t180b/03-spec2-title.png`).
- v2.00 on the same emulator (shipped test5 library, same launch contract, v2.00 ISO) plays its opening at 21.5 VBlanks/s
  and reaches the same kind of title screen: **GRAN TURISMO 4**, `Arcade Mode` / `Gran Turismo Mode`,
  `©2005 SCE` (`build/evidence/t180b/06-v200-title.png`).

**Gates.** Windows CTest serial 324/324 (1 skipped) and the Python suite 802 OK (48 skipped) were re-run for the shared
code of the first pass; this second change touches `android/native/CMakeLists.txt` only, and the v2.00 Android configure
does not enter either Spec II block (no `sif.cpp` splice, no definition), so the v2.00 library is unchanged.

## 2026-11-06 — TASK-185 backend: the Android on-screen virtual pad

Built the game side of TASK-185 (branch `task/185-virtual-pad-backend`, from `task/180-android-emulator` at 224f5460):
an on-screen pad for a phone with no controller, drawn over the game picture, fed into the same port 1 pad state a
physical controller feeds. The launcher editor is a parallel branch; the two meet only through the layout-file contract.

**Design.** The layout model and the input mapping are separate files of one pure C++ unit (`native/virtual_pad.{hpp,cpp}`),
so a later task can swap layouts by game context without touching the input path: `Pad::set_layout` takes another
`Layout`, the elements' `binds` are what the maths reads, and `on_vblank`, `merge` and the JNI seam stay as they are. The
Android activity only draws (from a flat float geometry the native pad returns, with the bind names for the PlayStation
symbols) and forwards touches; it holds no PS2 knowledge.

**Input.** `nativeVirtualPadTouch(element, dx, dy, down)` → buttons at full pressure (255), sticks as the two analog
bytes (128 at rest, the thumb's offset from where it landed, circular clamp, dead zone 0.08). `on_vblank` merges into the
polled state: buttons OR, pressure max, each axis the value further from rest; then the usual
`ps2::set_pad_buttons/axis/pressure`. The input recorder keeps the merged state. A pad that is hidden releases everything
it held (and so does a window focus loss), so no button can stay pressed.

**Visibility.** `auto` (default) follows Android's `InputManager` device list and its add/remove/changed callbacks,
`always` ignores it, `off` never builds the overlay. `GT4_VIRTUAL_PAD` travels from `[controls] virtual_pad` through
`gt4l_core::launch::virtual_pad_environment` (auto when the editor's setting row is absent from the build) and
`android.rs`.

**Tests.**
- `native_virtual_pad` (CTest, `native/virtual_pad_fixture.cpp`): the shipped default layout parses to the contract's 12
  elements in order; truncated/syntax/array/version/empty files are refused with a position; six kinds of skipped element
  each with its log line; coordinate and size clamping; no player file, a valid one and a broken one (falls back with its
  reason); stick maths (rest, dead zone edge, full right, up, half travel, circular corner 218/38, zero dead zone,
  clamped dead zone, not-a-number); d-pad threshold and diagonals; the merge (OR, max pressure, furthest axis); the live
  pad (press, release, hide, invisible element, bad index, log lines, geometry). Passes.
- `gt4l-core` launch contract: 34/34, including `the_virtual_pad_mode_is_a_stored_choice_with_auto_as_default`.
- Emulator (emulator-5554, APK `1.3.0-android-test6`, x86_64 library, `build/evidence/t185/`):
  - the pad over the publisher screen with no controller (`03`, `05`), a held Cross (`07`), the stick's knob moved up-right
    (`08`);
  - the game's own lines: `[vpad] cross down`, `[vpad] cross up`, `[vpad] lstick x=128 y=128` → `x=204 y=216` →
    `lstick centred`, `[vpad] hidden: Xbox Wireless Controller connected`;
  - `GT4_VIRTUAL_PAD_TEST_CONTROLLER` (a debug.env hook that reports one device event through the same refresh the
    Android listener calls) hid the pad eight seconds in (`06`);
  - a two-element player layout at opacity 0.8 was drawn as written (`09`); a broken one fell back with
    `player layout is not usable (the layout has no usable element (checked 1)); the default is used`;
  - F7 over the overlay: two taps gave `touch button: interval started (F7)` and `report written (F8)`.
- Not reached: a guest screen that reacts to input. The emulator renders through software Vulkan (`-gpu lavapipe`) on a
  host shared with other agents and ran the guest at about 0.4 VBlanks/s (F8: `EE gs_drain ms/frame=2767`, `[core2]
  draw=1111 ms`, `measured_thread_cpu_ms/frame=2.271`), where the TASK-180b runs on the same emulator reached 20-24
  VBlanks/s. The pad state itself is proven by the game thread's `[vpad]` lines, written at the VBlank that applies it.

**APK details.** The default layout is packaged from the repository through a Gradle `assets.srcDir` on
`android/virtual-pad` (asset `assets/default-layout.json`), so the app and the editor read one file. The library was
built for x86_64 for the emulator; an arm64 build for phones comes from the same configure script.

## TASK-185 launcher: the virtual controller editor (2026-11-06, afternoon)

The owner asked for the phone's on-screen pad to be customisable in the launcher. The backend agent builds the overlay and
the input path; this branch builds the launcher's settings row and the layout editor, and the two meet only through the

  comes from the same `Platform` rule): the Auto / Always / Off row (Auto is the default and a missing value), Edit layout,
  Reset to default, the layout's global opacity and vibration, and a status line that names the player's layout, the

- **Editor** (`ui/js/pages/virtual-pad-editor.js`, model in `ui/js/virtual-pad-model.js`): a full-screen landscape canvas
  over a dimmed race scene (CSS only, no artwork), the shapes 20:9 / 16:9 / 21:9 (the choice is remembered while the app
  runs), touch drag, pinch and a corner handle to resize, a tap to select; the selected element's size, width (only wide
  buttons), opacity and shown/hidden; the layout's opacity, vibration and snap to grid (2%); Undo (30 steps), Reset to
  default (loads the built-in layout into the editor, so Cancel still throws it away), Save and Cancel (with a discard
  confirmation). The F7 corner is drawn as a reserved zone (5% x 13%) and warns when an element overlaps it; elements are
  clamped inside the screen while moved or resized; the file keeps screen fractions and a preview shape never rewrites them.
  Keyboard and pad: Tab or the D-pad selects, A on a chip gives the element to the canvas, the arrows (keyboard) or the left
  stick (pad) move it, Shift+arrow or LB/RB resize, X undoes, Y resets, B goes back. The editor traps Tab and takes the
  D-pad/arrows before `nav.js` (a new `GT4.hooks.vertical` next to `horizontal`), so nothing behind it moves.
- **Width is a fraction of the screen width.** The contract says `size` is a fraction of the height and, when `width` is
  absent, the element is square. The default layout's L1/L2 pair (0.30 and 0.13, both 0.16 wide) only sits side by side
  with `width` measured against the screen width, and its circle at 0.96 only fits at 20:9 with a square's width as
  `size * height / width`. That is what the model and the editor implement; the backend must use the same rule.
- **Rust** (`gt4l-core/src/virtual_pad.rs`): version 1 types, the contract's validation (types, binds, ranges, duplicate
  ids, at most 32 elements, a stick-only dead zone), unknown fields ignored, an unknown `binds` dropped with a note, a
  newer `version` kept and locked. `load` returns the built-in layout with notes when there is no file or it cannot be
  used; `save` writes `virtual-pad.json.tmp` and renames it; `reset` deletes the file (and a leftover temporary file).
  Commands `get_virtual_pad` (mode, layout, the built-in layout for the editor's Reset, source, locked, has_file, notes,
  path), `save_virtual_pad` and `reset_virtual_pad`; the row is left out of the settings table like the controller row and
  drawn by the Controls page. 17 core tests and a launcher flow-audit test (save, reopen, refuse an invalid layout without
  touching the file, reset twice).
- **Texts** in en-US and pt-BR: 56 keys each (985 in both files), same placeholders; the element names reuse the Controls
  page's own names.
- **Checks.** `cargo test --workspace`: 797 passed, 0 failed (gt4l-core 311, gt4l-tauri lib 150, including the two new
