## Owner fidelity directive for CoreGS 3.0

The owner confirmed (Telegram, 2026-11-10): CoreGS 3.0 does not need to match CoreGS 2.0/GSdx pixel for pixel; the goal
is to get close and then iterate on lights, reflections and missing effects. The measured image and performance gates
are a compass, not a bit-exact acceptance gate. This matches the AGENTS/TASK-090 wording ("fidelity is a measured,
per-scene target, not a bit-exact gate"); it is recorded here as the owner's confirmation for the implementation work.

## Owner clarification: 100% decoupled presentation (CoreGS 3.0)

The owner clarified (Telegram, 2026-11-10) that CoreGS 3.0's presentation must be fully decoupled from the guest's 60 Hz
tick, like a modern game: an arbitrary, constant presentation rate (20, 30, 45, 60, 120, 144 Hz or VRR) with a stable
frame time, not the uneven cadence of CoreGS 2.0's frame skipping. The renderer samples the timeline at the presentation
instant and interpolates the two latest 60 Hz guest states; it cannot ask the guest physics for an arbitrary instant
because the game only computes at 60 Hz. Prediction/extrapolation remains an optional later switch; the default
interpolation costs about one guest frame of latency. The plan section 5.5 and the timeline structures already cover
this; wiring the presentation scheduler into the live renderer is still pending.

## Prediction study: rigid predictor and pose camera (2026-11-10)

- Three 32-frame windows of the deterministic B-Spec night race (seq1 7398-7429, seq2 8000-8031, seq3 9500-9531; static
  camera, followed car, fast pan/zoom) measured prediction vs the captured tick.
- Entrywise matrix extrapolation is exact for car bodies and the camera (<=0.05 px) but distorts spinning wheels by
  12-22.6 px at 1x (36-68 px at 3x) in every window (wheel spin 0.8-1.3 rad/tick). It is not safe globally.
- A rigid predictor (linear world translation, quaternion constant angular velocity, linear scale) with an entrywise
  fallback for rank-deficient flat shell/reflection draws gives a tick correction of <=0.37 px for bodies and <=0.9 px
  for the worst followed-car wheel at 1x (2.7 px at 3x), p95 <=0.2 px.
- The camera must be predicted from its pose (position + orientation) with a constant angular acceleration term:
  entrywise V extrapolation shifts a fast pan by 0.56-0.75 px, the pose model by 0.04-0.08 px.
- Interpolation needs the same rigid treatment for wheels: entrywise lerp wobbles them by 0.9-6.1 px at 120 Hz; rigid
  slerp is <=0.42 px. A player-car-only hybrid is not justified; the split is part-class and camera-driven.
- Discontinuities (collisions, resets, camera cuts) must drop the prediction for that tick. The study covers straight
  near-constant-speed B-Spec running only; braking/cornering, human input, collisions, cuts and course objects are
  unmeasured. Evidence: `build/analysis-prediction/`.

## Per-item capture: the light state, selector and carried block (2026-11-10)

Branch `task/090-capture-complete` (from `task/090-coregs3` at `f934a431`), merged into the main task branch. One code
step: make the `.gt4scene` capture carry the light state every car-pass draw's VU1 program actually used.

- **Format version 4.** `CapturedItem` gains the light state of the item's run (`light_block[16][4]`, the raw UNPACK
  word and source, and `light_source` = none/uploaded/carried/carried_uncertain) and the ITOP/MSCAL pair that ran it;
  `CapturedDraw` gains `chain_tags`, `chain_valid` and `program_uniform`. Versions 1-3 are refused; the fixture
  round-trips the new fields and the refusals.
- **Chain walker (`native/coregs3/coregs3_chain.*`).** `func_0049D328` writes the draw into the PGL output buffer as a
  DMA1 chain; the walker parses CNT, REF item/light tags and the terminator with the caller's guest-read function. The
  K1 post hook walks every hooked shape call; 822,826 chains, 0 incomplete.
- **Per-item light blocks.** The light tag is copied while `func_0049D1A0`'s per-draw counter (starts at 2) is nonzero,
  so the first two items of a light draw upload; the flag 1/4 paths that re-prepare per item upload every item. Frame 0:
  177 uploaded + 158 carried of 335; whole run 200,339 uploaded / 179,944 carried / 3,305 uncertain. The body family's
  items agree; the nine-qword family's differ within a draw.
- **Per-item selector.** The ITOP changes inside 8 of 116 draws in frame 0 (draw 98: 0x7B items 0-16, 0x161 items
  17-30); the MSCAL stub differs in 43 draws. Whole run: 52,362 items with a different ITOP, 91,205 with a different
  MSCAL; 0 without a run pair. This corrects round 13's "all items share the pair".
- **Carried block.** The EE cannot read VU1 memory (`g_vu1_mem` is on the MTVU worker; the EE shadow uses `g_dry_run`),
  so the capture tracks two slots in VIF command order keyed by the MSCAL parity (double buffer, `ofst 435`) and marks a
  carried block uncertain after a discontinuity when the slots differ. A frame replay predicts all 158 carried blocks of
  frame 0; the exact alternative (a `run_vu` hook capsule) is documented, not implemented.
- **Checks.** v3 field identity on 232 draws, CTest 4/4, Python 7/7, 3x off/shadow gate COREGS3-NIGHT-CHECK-OK
  (8,997 VBlanks, 1,686 racing, 0 differences, 13/13 frames). Evidence: `build/evidence/coregs3-r14/` (v4 capture
  819,808 B; tap 24,811,512 B), `build/evidence/analysis-090/`, `docs/COREGS3-HOOKS.md` §13.

## Owner readback directive (2026-11-10)

The native path targets zero per-frame readbacks: effects run on the GPU (flares by occlusion queries, reflections in a
GPU target, particles native). One-shot readbacks (photo mode, screenshots, car icons) and any value the game logic
actually consumes are kept, but delivered without stalling the frame. The TASK-087 study maps the GS readback call
sites; CoreGS 3.0 replaces them one by one.

## Car textures: the SLM sidecar and the native decode (TASK-090, branch `task/090-texture-decode`)

- **Sidecar.** `GT4_COREGS3_VRAM=<file>` in CoreGS 2.0 `core2::Renderer::Flush` copies a bounded SLM block range once
  per captured VBlank (default the measured car set 0x2BC0..0x38FF, 868,352 B) and writes a versioned `.gt4vram` file at
  shutdown. `GT4_COREGS3_VRAM_VBLANKS`, `_BLOCKS` and `_MAX_FRAMES` bound it; it reads only the CPU shadow memory and
  adds no guest I/O. The GS worker's record `vblank = V` covers the capture frame `frame.vblank = V - 1` (the frame
  whose interval ended at that VSYNC); the tool applies that rule.
- **Decoder.** `native/coregs3/coregs3_texture.{hpp,cpp}` (in `gt4_coregs3` for `GT4_HW_GS` builds) parses the 40-byte
  PGLUtexture record, decodes T4/T8/CT32 against a sidecar record with hw_gs `LocalMemory`/CLUT/`hw_gs_replace`, and
  returns RGBA8, width/height, Format G and Format P keys. Every unmeasured state is a named refusal.
- **Measured correction.** The first palette model (hw_clut `PeekLoad` with the record's own T4 profile, CSA applied at
  load time) matched draw 2 (CSA 0) but not draw 3 (CSA 6): the reference showed the 16x16 bank's group 6. The correct
  model is the full 32-bit CSM1 bank loaded unshifted with CSA applied at sampling by `DecodeHalfwords`; with it, both
  draws reproduce the CoreGS 2.0 `GT4_HW_DUMP_TEXTURES` PNGs byte for byte (`5d6616a3c740d56a-3013bc5012c5f0-00001554.png`
  and `19b46aeda67bdc9-a03e7dc7de2a8b02-00001554.png`). `hw_clut`'s own model is left untouched (CoreGS 2.0 gates).
- **Evidence.** Night race, 3x, bench card, 7,500 VBlanks: capture 819,808 B (frames 7398/7399, 116 draws, 169 texture
  records each), sidecar 2,605,152 B (records 7398-7400), reference dump 1,481 PNGs. Frame 0: 204 per-draw texture decodes,
  0 refused, 148 exact reference matches; T8 4/5 exact; the CT32 256x256 env map decodes but has no reference
  (a target, not a memory texture). Draw 2/3 are exact in both frames and their keys/RGBA are equal across
  7398/7399 (`aaaa07528cd1c1ea/003013bc5012c5f0`, `34f6bba4ed22ef60/a03e7dc7de2a8b02`). Evidence under
  `build/evidence/coregs3-td/`.
