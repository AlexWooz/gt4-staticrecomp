## Owner fidelity directive for CoreGS 3.0

The owner confirmed (Telegram, 2026-11-10): CoreGS 3.0 does not need to match CoreGS 2.0/GSdx pixel for pixel; the goal
is to get close and then iterate on lights, reflections and missing effects. The measured image and performance gates
are a compass, not a bit-exact acceptance gate. This matches the AGENTS/TASK-090 wording ("fidelity is a measured,
per-scene target, not a bit-exact gate"); it is recorded here as the owner's confirmation for the implementation work.

## Owner clarification: 100% decoupled presentation (CoreGS 3.0)

The owner clarified (Telegram, 2026-11-10) that CoreGS 3.0's presentation must be fully decoupled from the guest's 60 Hz
tick, like a modern game: an arbitrary, constant presentation rate (20, 30, 45, 60, 120, 144 Hz or VRR) with a stable
frame time, not the uneven cadence of CoreGS 2.0's frame skipping. The renderer samples the timeline at the presentation
instant and interpolates the two latest 60 Hz guest states; it cannot ask the guest physics for an arbitrary instant
because the game only computes at 60 Hz. Prediction/extrapolation remains an optional later switch; the default
interpolation costs about one guest frame of latency. The plan section 5.5 and the timeline structures already cover
this; wiring the presentation scheduler into the live renderer is still pending.

## Parallel wave: research rounds 14-16

- **Round 14 (remaining VU1 families).** All seven unlit families decoded and validated against the r13 tap: 9-qword
  first-power (0x0B48/0x0290) and power-16 (0x03D8/0x0418), 3-qword gain/clamp/bias (0x1508), the 6-qword no-colour
  Phong-style specular (0x0CA8) and the no-block pass-through (0x00B0). Residuals are max 1 level and alpha exact where
  the item's own block is captured. The light block is per item/material, not per draw; the v3 capture stores only one
  per draw, which explains the unmatched items. Tooling: the Python V2 format row was fixed and a VU1 simulator matches
  the AOT fragments. Evidence: `build/analysis-lighting/r14/`.
- **Round 15 (texture pipeline).** The car pass uses T4 (163/169 records), T8 (5) and one CT32 256x256 env map; CT32/CSM1
  palettes, no mipmaps, MODULATE, alpha test/basic blend. The 40-byte PGLUtexture record describes TEX0/TEX1/CLAMP; the
  capture has no pixels, palettes or per-pass GS state. The model UV is s16/4096 with no V flip (the current decoder
  divides by 65536 and flips V); the C++ tap parser misreads RGBAQ/ST/UV and lacks A+D. The smallest unblock is a GS-side
  SLM snapshot (~784 KiB/frame in the car block range) plus CoreGS 2.0's decoded textures as the reference. Evidence:
  `build/analysis-textures/`.
- **Round 16 (fog, GS state, effects).** Fog parameters are in PGL +0xFA0 (already captured): `t = clamp(u/w,0,1)`,
  `F = clamp(trunc(alpha + inverse*t),0,255)`, 99.83% within +/-1 on 4,659 vertices; FOGCOL is only in the tap, not the
  capture. The car pass uses AFAIL KEEP, DATE on the additive env-map pass, GS truncating blends, ZMSK=1 on reflections,
  no culling, COLCLAMP=1 default. The reflection is a second pass with the CT32 env map; the body fragment writes the
  reflection ST at TOPS+0x40, and the exact scale remains open. Priority: fringe-family lighting first, then fog, then
  textured paint, then the env-map reflection. Evidence: `build/analysis-effects/`.

## Per-item capture: the light state, selector and carried block (2026-11-10)

Branch `task/090-capture-complete` (from `task/090-coregs3` at `f934a431`), merged into the main task branch. One code
step: make the `.gt4scene` capture carry the light state every car-pass draw's VU1 program actually used.

- **Format version 4.** `CapturedItem` gains the light state of the item's run (`light_block[16][4]`, the raw UNPACK
  word and source, and `light_source` = none/uploaded/carried/carried_uncertain) and the ITOP/MSCAL pair that ran it;
  `CapturedDraw` gains `chain_tags`, `chain_valid` and `program_uniform`. Versions 1-3 are refused; the fixture
  round-trips the new fields and the refusals.
- **Chain walker (`native/coregs3/coregs3_chain.*`).** `func_0049D328` writes the draw into the PGL output buffer as a
  DMA1 chain; the walker parses CNT, REF item/light tags and the terminator with the caller's guest-read function. The
  K1 post hook walks every hooked shape call; 822,826 chains, 0 incomplete.
- **Per-item light blocks.** The light tag is copied while `func_0049D1A0`'s per-draw counter (starts at 2) is nonzero,
  so the first two items of a light draw upload; the flag 1/4 paths that re-prepare per item upload every item. Frame 0:
  177 uploaded + 158 carried of 335; whole run 200,339 uploaded / 179,944 carried / 3,305 uncertain. The body family's
  items agree; the nine-qword family's differ within a draw.
- **Per-item selector.** The ITOP changes inside 8 of 116 draws in frame 0 (draw 98: 0x7B items 0-16, 0x161 items
  17-30); the MSCAL stub differs in 43 draws. Whole run: 52,362 items with a different ITOP, 91,205 with a different
  MSCAL; 0 without a run pair. This corrects round 13's "all items share the pair".
- **Carried block.** The EE cannot read VU1 memory (`g_vu1_mem` is on the MTVU worker; the EE shadow uses `g_dry_run`),
  so the capture tracks two slots in VIF command order keyed by the MSCAL parity (double buffer, `ofst 435`) and marks a
  carried block uncertain after a discontinuity when the slots differ. A frame replay predicts all 158 carried blocks of
  frame 0; the exact alternative (a `run_vu` hook capsule) is documented, not implemented.
- **Checks.** v3 field identity on 232 draws, CTest 4/4, Python 7/7, 3x off/shadow gate COREGS3-NIGHT-CHECK-OK
  (8,997 VBlanks, 1,686 racing, 0 differences, 13/13 frames). Evidence: `build/evidence/coregs3-r14/` (v4 capture
  819,808 B; tap 24,811,512 B), `build/evidence/analysis-090/`, `docs/COREGS3-HOOKS.md` §13.
