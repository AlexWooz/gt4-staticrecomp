**Where the time goes (from the existing evidence, not from new runs).**

- **1x / CPU:** the GS worker is the largest renderer thread. On the rc14a Spec II George V Paris lap it is 8.0 ms of a
  16.2 ms process CPU, and the CLUT path is 2.0 ms, of which 1.5 ms is the batch flush a CLUT load forces; there are
  1,494-1,631 such flushes per VBlank (C, `docs/GAME-CODE-OPTIMIZATION-STUDY.md` section 9). The first license B-1 on
  the i7-11800H is 26,000-27,000 primitives and 1,930 batches per VBlank, GS 19-20 ms, VU1 15, EE 13, GPU 7-10, with a
  flat per-primitive profile (C, TASK-171). The 3x night race after PGO/ThinLTO is GS 5.14 ms, process 15.72, wall 8.33,
  frame p50 7.84, GPU 3.86 (C, IN-473).
- **6x / wait:** the Avell at 6x has the GPU about 14.1 ms busy but the GS worker waits 4.5-5.5 ms per VBlank at the
  game's one 2 KiB flare-table download; `GT4_CORE2_DELAYED_DOWNLOADS=1` removes the wait (wall 15.9-17.1 -> 14.6-14.7,
  frame p50 17.1-17.9 -> 15.5-15.6) but the owner rejected the one-frame-late answer in normal mode (C, TASK-134
  section 9; decision 0073). IN-522 already removed the EE's part of the wait (EE at the read 0.00 ms; 122/122 frames
  identical); the GS-worker part remains.
- **12x / fill:** 20.6-21.6 ms GPU busy, draw passes 14.7 ms, 563 M fragments, frame p50 22-25 ms; the 30 FPS mode is
  12.52 ms per drawn frame (C, IN-438/IN-442/IN-451/IN-463/IN-525). The largest 12x groups are the full-screen constant
  blends and the frame/depth traffic of 165 MB targets (C, IN-523).
- **Pacing and readbacks:** the frametime wave (IN-509), the race start (IN-510), the second presentation queue
  (IN-514..IN-519), the readback before a write (IN-508: readback phase 6.91 -> 2.76 ms at 6x) and frame skipping/30 FPS
  (IN-524/IN-525) are measured and in the ledger; they are not re-opened.

**New opportunities found in the code (not in the ledger).**

1. **SCISSOR and XYOFFSET should not end a batch in CoreGS 2.0.** `DecideFlush` rule 2
   (`frontend/hw_front_end.cpp:675-680`) flushes on TEST/SCISSOR/XYOFFSET/SCANMSK/DTHE together. The front end already
   clips each primitive's coverage to the live scissor (`ShouldDraw`, `hw_front_end.cpp:551-627`) and stores it in
   `PrimRecord::rect` (`AppendPrimitive`, 639-657); the vertices already carry XYOFFSET
   (`core2_gpu.cpp:3313`). `TranslateBatch` re-applies the batch snapshot scissor at
   `writeback/hw_gs_writeback.cpp:539`, which is the only reason the flush is needed. Use `PrimRecord::rect` as the
   per-draw scissor for CoreGS 2.0 and leave TEST/SCANMSK/DTHE flushing. Exact; small; possibly a large batch reduction
   on the license and George V. No ledger row mentions SCISSOR or XYOFFSET (searched the ledger, CPU survey and
   game-code study). The existing `[core2] batch flushes/vblank` line prints `test=` as one number; split it before
   claiming a gain.
2. **GPU-side flare modulation** (GS-READBACK-STUDY S4, never scheduled). Nothing on the EE reads the 64x8 table; only
   the VU1 flare program does, through a VIF REF. Replace the REF'd qword with 0xFF, mark the VU1 job that uses it and
   modulate the flare draws in the vertex shader from the table target. Same frame, faithful, ±1 LSB on flare pixels;
   removes the measured 4.5-5.5 ms GS-worker wait at 6x and ~1.3 ms at 1x. Precondition P1: the VU1 program must use the
   value only as a linear colour/alpha factor; run the AOT/interpreter differential harness with visibility 0..255
   first.
3. **CLUT-flush scope.** The flush is unconditional for every indexed pending batch
   (`hw_front_end.cpp:372-390`). The CLUT buffer is one 512-halfword buffer; a load writes at most two ranges
   (`ClutHalfwordsWritten`, `core2_renderer.cpp:894-911`) and a texture reads a known set
   (`ClutHalfwordsUsed`, 914-927). If the ranges do not intersect, the load changes no halfword the pending batch uses
   and the flush can be skipped. The existing helpers are already used for the GPU CLUT key (`GpuPaletteKey`, 929-939).
   This is not TASK-134's dropped whole-palette identity probe (5%); it compares ranges, not bytes. Cheap and exact; a
   partial step before TASK-168.
4. **Effect-target scale cap** beyond IN-497's 1x/width 256 in Performance Mode
   (`core2_renderer.cpp:571-574`, `1842-1844`; `Image::scale` is per image and `pushTexScale` already carries a
   texture's own scale). Measure the target sizes/fill at 6x and 12x with `GT4_CORE2_GPU_PROFILE_AT` first.
5. **Self-copy off in Performance Mode at 12x.** IN-463 measured the copy at +1.3 ms of GPU busy at 12x (+6%, frame p50
   22.5 -> 24.8) and without it 17-21 of 31 frames differ; the A/B (`GT4_CORE2_SELF_COPY=0`) already exists. A
   Performance Mode variant is a different design from the kept faithful path.
6. Recorded but lower/measurement-first: fuse the display compose with the present downsample (E), a target-table index
   for long sessions (G), and the GS worker's per-record backend mutex (small). The submission thread and TASK-168/
   TASK-171/TASK-162 are already known and are not repeated.

**Do not repeat.** The audit lists IN-412/413 (content caches), IN-421/436/438 (fragment shader/read skipping), IN-443/
444/449 (compute sprites, hardware bilinear, gather), IN-448 (MTVU slot rings), IN-454/460 (whole clears, patch kernel),
the 32/64/128 submission sweep, IN-472/523 (D1/ROP), IN-488 (thread pinning), IN-505 (colour filter), the one-frame-late
flare answer in normal mode, IN-537/539 and the GSDX-PLAN G5/G6/P3 items, each with its measured result.

**Short list for TASK-215 (ordered).** (1) SCISSOR/XYOFFSET batching; (2) GPU flare modulation; (3) CLUT-flush scope;
(4) effect-target scale cap in Performance Mode; (5) self-copy off in Performance Mode at 12x. The prerequisite is a

## TASK-215c: CoreGS 2.0 waits and async audit (read-only)

**What this was.** The owner (2026-11-10, 17:21 and 17:26, voice) said the CoreGS 2.0 bottleneck is **waits**, not
rasterisation: the current PC hides it, the target is weaker hardware (Galaxy S23 Ultra class, tile GPU), and the
synchronous mode must become as asynchronous as possible — while the GPU waits for an EE readback (the flare visibility),
it should start the next task/frame; when the answer arrives, finish that task, present, and resume; or parallelise
inside the GPU; never let waits block. Frame skipping is only for occasional 59/58 dips; 30 fps is the last resort;
normal mode keeps the same-frame flare. This was a read-only audit in the same worktree and branch as TASK-215b, docs
only: no build, benchmark, game run, code/data/pin/test change. Not PCSX2-tainted; no PCSX2/GSdx/fork/ARMSX2 source; GSdx
is a black box.

**The pipeline.** It is half asynchronous: the EE is 2 VBlanks ahead (`kFramesAhead=2`, `hw_gs_stream_sink.cpp:508`), the
GS worker has 8/16 submissions in flight (32/64 batches each; `core2_gpu.cpp:205-218`, `2471-2472`), and the second
presentation queue decouples the display when the graphics family has two queues (`hw_gs_backend.cpp:686-688`). The EE can
run ahead until the VBlank back-pressure/rings fill; the GS worker records ahead until the slots fill. **There is no
separate submission thread**: `Gpu::submit` runs on the GS worker (`core2_gpu.cpp:2188-2212`); the `pacer_thread` exists
only for frame skipping; the `frametime` thread only reads present times.

**The hard synchronous point.** The flare readback is once per race frame: the GS worker executes the read at its stream
position (`hw_gs_stream_sink.cpp:682-688`), `Readback` (`core2_renderer.cpp:2643-2731`) submits a full reduction and
`wait_all`/`vkWaitForFences` on every in-flight slot (`core2_gpu.cpp:4089-4119`, `2143-2148`, `2103`). The VU1 worker
cannot produce the flare draws until the bytes arrive (`hw_flare_table.hpp:65-69`, `85-92`); the VU1 output after the read
does not exist; the GS worker has nothing after the read; the GPU finishes the work before the read and idles. The EE no
longer waits (IN-522), but the rings only move the stall. Measured 4.5-5.5 ms per VBlank at 6x, 1.3 ms at 1x (C, TASK-134
section 9); the 373 build had 3.80 ms of reads and 3.42 ms of GPU waits; the final 374 table shows the EE at the read at
0.00 (C/H, ledger 373/374).

**Every other wait mapped.** The one-queue present (`vkWaitForFences` `hw_gs_backend.cpp:1414-1416`,
`acquire_image(UINT64_MAX)` `1419`) measured 11.42 ms in the showroom and 17-33 ms in races at 60 Hz; the second queue
0.01 ms (IN-516). The submission-slot fence (`core2_gpu.cpp:2099-2140`, `2150-2157`): 8/32 integrated; the comment at
205-208 records the GS thread waiting "on every heavy stretch" with 25-45 submissions per 6x VBlank. The tone-hook CLUT
readback (`core2_renderer.cpp:1075-1089`, `3278-3337`; `core2_gpu.cpp:3994-4008`): a `submit(true)` full wait per colour-
filter run, **not attributed** by the `gpu_wait by reason` line. The before-write/keep stores (`core2_renderer.cpp:2826-
2909`, `1734-1765`): IN-508 took the before-write case 3.00 -> 0.00 per VBlank and the phase 6.91 -> 2.76 ms at 6x; the
remaining stores are the showroom/photo/keep. The one-shot reads (`hw_gs_stream_sink.cpp:858-901`, `591-599`): the EE
drains the GS worker and reads the GPU; the race-start camera cut is 27-33 reads/about 42 ms once (IN-429/430). The
MTVU/VU1 chain (`mtvu_runtime.cpp:565`, `762-769`; `mtvu_journal.cpp:194-235`): the download 3.34 ms at 1x night before
IN-461, the flare read no EE wait after IN-522, the VBlank drain 1.08 ms at 1x day. The pacer/audio waits
(`window.cpp:618-657`, `frame_clock.cpp:49-77`, `host_io.cpp:471-494`) are cadence, not the renderer bottleneck. Locks
(`hw_gs_stream_sink.cpp:735-740` per record, the flare condition variable, the replacement/pacer/frametime/spec
condition variables), allocations (`vkAllocateMemory` blocks; IN-424/IN-418) and pipeline warm-up (97 variants, 128 ms
each, IN-437; prepare/cache IN-507/489) complete the map. `vkDeviceWaitIdle`/`vkQueueWaitIdle` are only resize/shutdown
on the CoreGS 2.0 path; the `native_vulkan.cpp`/`hw_gs_writeback_gpu.cpp`/`gs_stream_ipc` waits are CoreGS 1.1 or the
external process, not this path.

**Async list.** (1) GPU-side flare modulation (S4: replace the REF with 0xFF, mark the VU1 job, modulate the flare draws
from the 64x8 target; same frame, exact; the per-frame drain disappears). (2) One-queue present decoupling: search a
present-capable family (the code uses only the graphics family's `queueCount >= 2`), or a presentation thread on one
queue. (3) Submission-ring depth/submit interval on the target (`GT4_CORE2_SLOTS` 8/16/24, `SUBMIT_EVERY` 32/16/8; the
8/32 integrated default was chosen for the HD 620). (4) Tone CLUT decoded in the tone shader from the GPU CLUT instead of
`ReadClut`. (5) Before-write/keep on the GPU (GLM newest copy, TASK-162; the block patches IN-512/538; IN-539 off).
(6) Independent submission thread (known 0.3 ms; more on a phone). (7) Mobile shader prepare/cache. The 12x fill ceiling
is not a TASK-215c target; the CPU/GPU items A/B/D/F of TASK-215b are complementary (they shorten the work between waits).

**Mobile/tile notes.** A readback is a resolve/flush of tile memory, not a copy; a barrier can flush tiles; the
storage-image/`VK_IMAGE_LAYOUT_GENERAL` path bypasses tile-local fast paths and framebuffer compression; async compute may
share the shader cores/tile memory and not overlap; the one-queue present blocks the producer; UMA memory pressure and
`vkAllocateMemory` can stall; the mobile driver compiles pipelines on create; idle waits can keep the clock low and then
burst/throttle. These are architecture facts/prose, not ARMSX2/GSdx source. The S23 Ultra queue families, interlock and
async-compute support, wait split, thermal state and the GSdx comparison are Unknown until measured.

instrumented 60 Hz race scene on the S23 Ultra with the existing lines. No build, benchmark, game run, code/data/pin/test
change; no Telegram/PR/release/tag/draft; no owner data; no Avell target.

## TASK-215f: license B-1 tone/CLUT audit (read-only)

**What this was.** Follow-up to TASK-215d after the perf agent's rc15 measurement: `GT4_CORE2_PALETTE_SEGMENTS=1`
(TASK-168, off by default) gives no real gain on license B-1 (Test Course); the earlier 9.55 -> 8.99/8.71 was an outlier
(3 off 8.675/8.705/9.550 vs 2 on 8.705/8.990), with `clut_kept=0`, `segmented_batches=0`, `tone_refused=1.67M` in both.
The license is CPU-bound: GS 8.08-8.25, GPU 1.05, 1,430 CLUT flushes/VBlank (1,010 same texture), `gif_parse` 3.80. The
TASK-168 segment path is in the TASK-215/rc15 worktree (`gt4-wt-215-coregs2-perf`, `d18542f2`), read read-only; it is not
in this docs branch. No build, run, code/data/pin/test change; no PCSX2/GSdx/ARMSX2 source.

**Refusal cause.** The tone refusal is not a visibility/ordering impossibility. `ToneHook` can handle a segmented batch:
`OnBatch` splits it per segment (`core2_renderer.cpp:4170-4190`), each split batch's tone uses its own segment palette
(`DecodeSegmentPalette(batch,0)`, `3530-3531`), and the segment palette rows are ordered before the draw
(`core2_gpu.cpp:3785-3809`). The refusal is TASK-168b's **measured performance veto** (`PaletteSegmentBatchAllowed`,
`821-825`): during a tone run a T8 sprite batch (`ToneShape`, `870-873`) is a copy-back strip that `ToneHook` skips whole
(`3505-3512`); keeping/segmenting it and splitting it cost more than the flush (+3-4% GS thread on George V, `815-820`).
The license's 1,010 same-texture flushes are those strips; the filter refuses; `clut_kept=0`/`segmented_batches=0`; the
segment A/B measured nothing. The `tone_refused=1.67M` in both runs is **likely** the tone early-drop count (`DropOnArrival`,
`4158-4167`), not the segment filter's `paletteSegmentToneRefusals` (only installed with segments on, `995-999`); confirm
the exact counter, the label conflates them.

**Flush mechanism.** The 1,430 `clut` flushes are a **batch boundary from the CLUT load** (one palette per batch,
`hw_front_end.cpp:390-418`; `clutFlushSameTexture_` 1,010 at `415-417`), not a texture-cache/decode event; the 211 `prim`
and 170 `texture` are the other state flushes; `gif_parse` 3.80 is the TASK-171 per-primitive front end, not a flush
reason.

**Smallest exact design.** A **front-end tone-strip drop**: before the CLUT-load `FlushBatch`, ask the renderer whether
the pending batch is a tone strip (the same `ToneHook` predicate: `toneActive_`, `toneFbmsk_`, `PossibleShuffle`); if
so, discard it without flushing; the first batch of the run still reaches the renderer for the tone pass. Expected
**Hyp 1-2 ms** GS worker (the 1,010 flushes + batch work; scaled from the TASK-134 CLUT path), exact; frames identical;
the `GT4_CORE2_TONE_STRIP_DROP=0/1` A/B and the `hw_core2_tone` strip fixture. The unchanged-palette CLUT-flush scope
(TASK-215b B) is exact but cannot cut the 1,010 (their palettes change); it cuts the other CLUT loads. The segments under
the tone stay off (the +3-4% measurement); the `PALETTE_SEGMENTS` default stays off.

**Tone `ReadClut`.** Not on the license path: `SyncClutToCpu` returns before `ReadClut` when `GpuPaletteKey == 0`
(`1257-1276`); the license's palettes are CPU loads, so `clut_reads`/the `clut` wait are 0. The GPU-CLUT tone shader
(reading `s.clut` in `core2_tone.comp`) is a night/George V item (the `clut` wait reason, IN-546), not the license.

**Prioritized list.** (1) the front-end tone-strip drop; (2) TASK-171 per-primitive front end (`gif_parse` 3.80);
(3) the CLUT-flush scope for the non-tone CLUT loads; (4) SCISSOR/XYOFFSET batching; (5) the tone GPU-CLUT shader for
night/George V; (6) keep `PALETTE_SEGMENTS` off; (7) the texture/prim per-primitive design; (8) the owner's decision on
the game-effect-specific tone-strip skip.
