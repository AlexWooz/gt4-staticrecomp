### What the study found

- **Threading and submission.** GSdx records a frame into one command buffer and submits it at present (3 command buffers, 2 in
  flight). The only mid-frame submit is a kick armed for 3 frames after a synchronous readback, offered at render-pass
  boundaries only when the next command buffer is free. ARMSX2 adds a front/back split (GIF parse on MTGS, draws on a back
  thread), refused on non-Vulkan and when downloads read live memory, and refused by policy when the back thread would share a
  big core.
- **Readbacks.** Default is synchronous: copy into a staging buffer, fence wait on the GS thread, unswizzle into local memory.
  `Asynchronous` is a real mode: the EE reads a CPU shadow with no wait, the GPU copy is retired at a later VSync, per-page
  generations drop stale snapshots, the newest snapshot of a range wins, and a 1x1 read gets a fixed 3-frame latency so a
  visibility effect cannot oscillate. That is the owner's rejected lateness (decision 0073) made stable; it is not a
  faithful-mode technique.
- **The explicit overlap answer.** With the default mode the GS thread blocks and does not record the next frame while the
  fence is pending (the EE can still run ahead in the 8 MiB ring). With `Asynchronous` it overlaps, by 3-4 frames.
- **The mobile gap, in our numbers.** The S23 Ultra run of CoreGS 2.0 is 11.5 ms of GPU per VBlank at both 1x and 2x with ~750
  fragment barriers, 75 full barriers and 20 render passes per VBlank (owner's log bundle, private `TASKS.md` TASK-180). Their
  attachment model spends a pass boundary only on a target change and a barrier only on a real read-after-write. This is the
  mechanical reason GSdx can be much faster there, and it is TASK-182's subject, not a new discovery.
- **The desktop answer.** On the same recording and work, CoreGS 2.0 is 9.0% faster than `gt4-gs.exe` at 3x and 11.4% at 12x,
  wall clock including the transport (TASK-215 baseline). The study says so in its first section so nobody "fixes" the desktop
  with a mobile idea.

### Opportunities that survived the cross-check

1. TASK-182 (pass and barrier scope on tilers): already planned, ranked first, with their design as confirmation.
2. Pre-acquire the next swapchain image on the single-queue present path: their one present trick we lack; the ledger measured
   the stall it removes at 11.42 ms in the showroom on the 60 Hz virtual display (IN-521).
3. A pending-readback queue with per-page validity, only where lateness is already accepted (photo mode TASK-162; the
   Performance Mode delayed download if kept).
